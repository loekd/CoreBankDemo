# ADR-018: Add an opt-in instant-payment rail alongside store-and-forward

**Date:** 2026-09-02
**Status:** Accepted
**Deciders:** Architecture team

## Context

CoreBankDemo models exactly one payment rail: every payment is accepted with `202`, buffered in the payments outbox, and settled by a background processor; CoreBankAPI stores every command in its inbox and executes it on a processor loop. Real SEPA has two rails with materially different engineering constraints — an SCT Inst payment gives the payer's PSP, the payee's PSP, and the clearing mechanism nine seconds in total and runs 24/7/365, while a standard SCT settles in one to two business days in batches. A demo with only the batch shape cannot show a bounded end-to-end budget, an ambiguous timeout on a synchronous hop, or why retry/circuit-breaker/idempotency choices differ between the two rails — the properties that motivate most of the surrounding architecture.

## Decision

Add an opt-in instant rail alongside the existing one; remove nothing.

- **Wire contract (additive only).** `POST /api/payments` gains an optional `scheme` field, closed set `standard` (default) / `instant`. Absent or `standard` reproduces today's behaviour byte-identically. `POST /api/transactions/process` gains an optional `X-Execute-Mode: inline` request header. Absent reproduces today's deferred-execution behaviour exactly.
- **PaymentsAPI** persists and dedupes exactly as today (`PaymentStorageHandler` is untouched — AD-2). For a freshly-stored `scheme=instant` row, a new decorator (`InstantPaymentForwardingHandler`) claims the row through the kernel's per-row claim path (`IOutboxMessageStore<TMessage>.TryClaimByIdAsync`, new — reuses the same `Status`-as-concurrency-token transition `ClaimBatchForPartitionAsync` already uses, so an inline claim and a concurrent background batch claim can never both win the same row), then makes a budgeted, per-attempt-timeout-bounded inline forward via the same validate+submit sequence the background delivery strategy uses (`HttpForwardOutboxDeliveryStrategy` now also implements `ICoreBankTransactionForwarder`, extracted so both callers share one implementation). A committed outcome (CoreBank business success or business rejection) answers `200` and completes the row; a budget/attempt exhaustion, a transport failure, or the row already being claimed releases the claim back to `Pending` (via the existing `MarkAsFailedWithRetryAsync` transport-failure transition) and answers `202` exactly like the standard rail.
- **CoreBankAPI** keeps its inbox unchanged. When `X-Execute-Mode: inline` is present and `TransactionIntakeHandler` stores a brand-new command row, it invokes the same `IInboxMessageHandler<InboxMessage>` (`TransactionExecutionHandler`) the background inbox processor uses, inline within the request — no second execution code path, same atomic ledger/inbox-completion/event-enqueue commit (AD-5). If it throws, the row is left exactly as storage left it (`Pending`) for the processor to drain on its next pass; no partial commit, no event published.
- **New options**, `Payments:InstantRail` (`Enabled` default `true`, `BudgetMilliseconds` default `9000`, `AttemptTimeoutMilliseconds` default `2500`, `MaxAttempts` default `2`), validated at startup (Story 3.1 pattern): every value positive, and `AttemptTimeoutMilliseconds * MaxAttempts` must not exceed `BudgetMilliseconds`.
- **Response semantics extension of AD-11.** AD-11 already treats a business rejection as a successfully processed message (never `Failed`, never retried). This story extends that classification one level up the stack: on the instant rail, PaymentsAPI's `200`-vs-`202` decision is driven by whether CoreBank confirmed a *committed* outcome within budget — success or rejection both commit and both answer `200`; only "no committed outcome observed within budget" (an honest unknown) answers `202`. A budget timeout is therefore never mapped to `504` — the payment may already have executed, and `202`/`Pending` states that truth rather than inviting a client retry that could look like a second payment.
- **Frozen response shapes are not changed.** `PaymentResponse` and `TransactionResponse` carry no new fields; the instant rail communicates its outcome entirely through existing `Status` values (`Completed`/`Failed`/`Pending`) and the HTTP status code. This avoids any change to the checked-in CoreBank OpenAPI document or the generated Kiota client.
- **Metric contract additions.** `corebankdemo.payment.intake` gains a `payment.scheme=standard|instant` attribute on its existing point (no new instrument). A new histogram, `corebankdemo.payment.instant.duration` (`outcome=settled|rejected|deferred`), records once per instant-rail request when the inline attempt concludes or the budget expires.

## Consequences

- The standard rail is provably untouched: `PaymentStorageHandler`, `TransactionExecutionHandler`'s execution logic, and every existing response shape are unchanged; the new behaviour is reached only via the new `scheme`/header opt-ins.
- `IOutboxMessageStore<TMessage>` and `ICoreBankApiClient.ProcessTransactionAsync` gain new members/parameters. Both are additive (a new interface method; a new optional trailing parameter defaulting to today's behaviour), so no existing call site needs to change.
- No change to `LoadTestSupport`, `k6/script.js`, drain semantics, `PartitionCount`, lock lifetime, or claim semantics for the standard rail. The four-store drain and the k6 acceptance gate keep passing unmodified.
- A demo can now show a bounded, honest-uncertainty synchronous hop (the instant rail) side by side with the unbounded, fire-and-forget batch hop (the standard rail) — the pedagogical gap this story exists to close.

## Addendum: Review loop 1 (2026-09-03)

Two review findings, both confirmed against the running code, were resolved without changing the decisions above:

1. **Duplicate replay of a business rejection reported `Completed`.** `OutboxMessage` gains a nullable `ResponsePayload` column (mirrors CoreBank's own `InboxMessage.ResponsePayload`), populated with the serialized `TransactionSubmission` on every completed delivery — `HttpForwardOutboxDeliveryStrategy.ForwardAsync`'s single implementation, used by both the background path (`executeInline: false`) and the instant-rail inline path (`executeInline: true`) — never an instant-only special case. `PaymentsController`'s duplicate-replay path now derives the wire `Status` for a `Completed` row from that payload (`ResolveDeliveredStatus`), not the raw kernel `Status` column, which stays transport-state-only per AD-11 and never distinguishes a business success from a business rejection. The same fix also normalizes a duplicate hitting a still-claimed row (raw `Status = Processing`) to the matrix's documented `Pending` wire word, on the instant rail only — the standard rail's duplicate response is untouched and still surfaces the raw kernel `Status` verbatim, preserving byte-identical baseline behaviour.
2. **CoreBank inline execution could race the background processor into a double ledger execution.** `CoreBankDbContext` was missing `MessageRepositoryBase<InboxMessage, CoreBankDbContext>.ConfigureConcurrencyToken` on `InboxMessage` — `PaymentsDbContext`'s entities already had it, CoreBank's did not — so nothing detected a concurrent write to the same row. `IInboxMessageStore<TMessage>` gains `TryClaimByIdAsync`, mirroring the Payments-side `IOutboxMessageStore<TMessage>.TryClaimByIdAsync` exactly (inherited for free from the shared `MessageRepositoryBase` once the interface member exists). `TransactionIntakeHandler.TryExecuteInlineAsync` now claims the row via this method before ever invoking `TransactionExecutionHandler`; a lost claim falls back to `Accepted`/`Pending`, identical to an already-claimed row on the Payments side. The full CoreBankAPI and Persistence.IntegrationTests suites were re-run afterward (concurrency token is foundational, shared by the background processor) with no regression: 103 and 199 tests respectively, all passing, coverage unchanged at ≥90% line.

Both fixes are additive to the wire/metric contracts recorded above — no field, header, status code, or metric name changed; only a new nullable persistence column, a new kernel interface member (mirroring an existing one), and a missing EF concurrency-token configuration were added.

## Addendum: Story 7.4 operator-console acceptance hardening (2026-09-04)

The mixed-rail acceptance gate now measures FIFO ordering from each durable store's enqueue and processing timestamps. That exposed real overtaking in both inline paths: a later instant request could claim and complete its row before an earlier row in the same partition.

Both inline paths now acquire the same renewable partition lock used by their background processor and claim only when their row is the oldest claimable row in that partition. If the lock was never acquired, or earlier work exists, the request falls back to `202 Pending`. A third case is also now handled correctly: `IDistributedLockService.ExecuteWithLockAsync` reports `false` both when the lock was never acquired (the workload never ran) *and* when the workload ran to completion but lock ownership was lost mid-flight (its own contract: "not reporting success for work that ran without a guaranteed-exclusive lock") — a subsequent adversarial review found both inline paths were conflating these two cases and discarding a genuinely-completed result in the second, reporting `202 Pending` for a payment/transaction that had actually committed. Both paths now key their fallback decision on whether the claimed workload produced a result at all, not on the lock service's own boolean: a non-null result is always returned, even if the lock was reported lost afterward; only a null result (the workload never ran) falls back to `202 Pending`. This preserves the existing wire contract while making the documented "never deliver inline while another replica holds the partition lock" rule executable and keeping instant optimization subordinate to durable per-partition ordering, without ever downgrading a truthfully-committed outcome to a false pending.

## Addendum: Instant-rail dispatch priority (2026-09-04)

**Problem observed.** Under a mixed-rail burst, almost every instant payment answered `202 Pending` rather than `200 Completed`. The story-7.4 hardening above made both inline paths claim only the *oldest* claimable row in their partition, so an SCT Inst arriving while batch (SCT) work was queued in the same partition was deferred without an attempt — every partition's queue was head-of-line blocked by standard work. That contradicts the rails being modelled: an SCT Inst is settled individually within its nine-second budget, while an SCT is batch work that is in practice executed once a day. Nothing in the real world makes an instant payment wait behind a batch.

**Decision.** Dispatch order within a partition becomes *priority, then arrival*:

- `IMessage` gains `int Priority`. `MessageConstants.Priority.Standard` (`0`) is the default for every store and every existing row; `MessageConstants.Priority.Instant` (`100`) is assigned by `PaymentStorageHandler` for `scheme=instant`.
- Both kernel claim queries (`OutboxMessageRepositoryBase`/`InboxMessageRepositoryBase.GetClaimableMessagesQuery`) order by `Priority` descending, then the store's arrival timestamp, then `Id`. Because `ClaimBatchForPartitionAsync` (background) and `TryClaimByIdIfOldestAsync` (inline) share that one query, an instant row is first in line for the inline attempt *and*, if the attempt is deferred, is drained by the background processor ahead of queued standard rows.
- PaymentsAPI carries the priority to CoreBankAPI as an optional `X-Payment-Priority` request header on `POST /api/transactions/process`, sent only for a non-standard priority, so the standard rail's request is byte-identical. `TransactionIntakeHandler` stores it on the inbox row; absent, unparsable or non-positive values mean standard, so a caller can never delay a command by sending garbage. The frozen `TransactionRequest`/`TransactionResponse` shapes are unchanged.
- The acceptance gate's FIFO check (`LoadTestAssertionCalculator.FindOrderingViolations`) now compares rows only against rows of the same `(Store, PartitionId, Priority)`. FIFO remains a hard guarantee *within* a priority class: an instant row still never overtakes an earlier instant row, and a standard row never overtakes an earlier standard row. Overtaking *across* classes is the intended behaviour, not an inversion.

**Waiting within the budget.** Priority alone did not change the outcome under a concurrent burst (3 of 60 instant payments settled inline in a mixed 8-concurrent run): both inline paths still gave up at the first sign of contention — a non-blocking `TryAcquire(0)` on the partition lock, which every concurrent instant request in the partition and the background processor's 200 ms poll contend for, and a single "am I first in dispatch order?" check. The budget exists precisely to bound *waiting*, yet nothing waited. Both paths now wait: `IDistributedLockService` gains an `ExecuteWithLockAsync` overload with an `acquireTimeout` (a default interface implementation keeps every existing implementation and fake unchanged; `RedisDistributedLockService` passes it to `TryAcquireAsync`), and the inline paths re-check "first in dispatch order" every 25 ms — PaymentsAPI until its `BudgetMilliseconds` runs out, CoreBankAPI for at most 2 000 ms, deliberately under PaymentsAPI's default `AttemptTimeoutMilliseconds` of 2 500 ms. Both stop waiting the moment another claimant owns the row (`FindByIdAsync`, new on both store ports and already implemented by `MessageRepositoryBase`): that row is being delivered by the background processor and its outcome arrives through the transaction event. Only "not first yet" is ever retried — an inline execution failure is still never retried inline, exactly as the spec's matrix requires. The background processors keep the non-blocking form.

**Leaving a fresh instant row to its own request.** Waiting exposed the next race: with instant rows first in dispatch order, the background processor's 200 ms poll now claimed a freshly stored instant row *before* the request that stored it had reached its turn — the poller won that race for roughly two rows in five, turning a would-be `200` into a `202` settled a hundred milliseconds later by the batch rail. `IMessage` therefore gains `HoldUntil`: while set and in the future, the background batch claim leaves the row alone; the ordered inline claim ignores it. PaymentsAPI holds an instant row for its `BudgetMilliseconds`; CoreBankAPI holds an inline-mode inbox row for its 2 000 ms wait window. If the inline attempt gives up or its process dies, the hold lapses and the batch rail takes over exactly as before — a deferred instant is at worst delayed by the budget it was always allowed to spend. This is the same schema caveat as `Priority`: `ALTER TABLE "<store>" ADD COLUMN IF NOT EXISTS "HoldUntil" timestamptz NULL` on the four stores of a pre-existing database. Two implementation notes for the record: the "has another claimant taken my row?" check between wait iterations is a `Status` projection (`GetStatusAsync`), never an entity load — the request's scoped `DbContext` inserted that row and would hand back the tracked, still-`Pending` instance regardless of the database; and only "not first yet" is ever retried, so an inline execution failure is still never retried inline.

**What is deliberately unchanged.** Per-key ordering (AD-4) is untouched — a key has exactly one row, so priority never reorders anything for a single key. Exactly-once still rests on the row-level claim with `Status` as a concurrency token, not on ordering. The partition lock, budget, attempt timeout and every response code stay as recorded above. Instant rows still queue FIFO behind *earlier instant rows* in their partition and still take the non-blocking partition lock, so a burst consisting purely of instant payments will continue to defer most of them; relaxing that is a separate decision.

**Schema.** This repo uses `EnsureCreated()` only (no migrations), which never alters an existing table. Persistent databases created before this change need `ALTER TABLE "<store>" ADD COLUMN IF NOT EXISTS "Priority" integer NOT NULL DEFAULT 0` on `OutboxMessages`/`InboxMessages` (paymentsdb) and `InboxMessages`/`MessagingOutboxMessages` (corebankdb); fresh databases get the column from `EnsureCreated()`.

## Addendum: Committed-outcome recording gap on the deferred/async completion path (2026-09-04)

**Problem observed.** Operating the console (story 7.4) surfaced two related defects that together made a deferred instant payment show `202 Pending` forever, even minutes after CoreBank had genuinely completed it, and separately made an operator-supplied idempotency key on a fresh instant payment come back as a "malformed or mismatched response."

1. **Wrong outcome on a deferred/claimed row.** `InstantPaymentForwardingHandler`'s outcome mapping treated "the row was already claimed" or "the wait budget ran out" the same as a business rejection (`Rejected`), instead of the honest "no committed outcome yet" (`Deferred`). A row that was still genuinely in flight was reported as if CoreBank had already turned it down.
2. **Duplicate replay served a non-terminal cached payload as final.** `PaymentsController`'s duplicate-key path (`ToDuplicateResult`) answered `200` for *any* `Completed`-status outbox row with a cached `ResponsePayload`, without checking whether that payload actually recorded a committed CoreBank outcome (`Completed`/`Failed`) as opposed to a still-`Pending` one. Combined with (3) below, a resend of the same idempotency key kept echoing a stale, non-committed payload as if it were the final answer.
3. **The actual completion, when it arrived asynchronously, was never recorded.** When an instant payment's inline attempt was deferred, its eventual outcome arrives later out-of-band as a `com.corebank.transaction.completed`/`.failed` Dapr event into PaymentsAPI's inbox. `TransactionEventHandler` logged that event but never wrote it anywhere — the outbox row's `ResponsePayload` (the field `ResolveDeliveredStatus`, added in Review loop 1 above, reads to distinguish a business success from a rejection) was populated only by `HttpForwardOutboxDeliveryStrategy.ForwardAsync` completing synchronously. A payment that settled via the deferred/event path had no committed outcome recorded anywhere for a future duplicate query to find.

**Fix.** `IOutboxRepository` gains `RecordCommittedOutcomeAsync(transactionId, status, processedAt, ct)`: loads the tracked row by `TransactionId`, no-ops if a committed outcome is already recorded (idempotent against event redelivery), otherwise serializes a `TransactionSubmission` into `ResponsePayload` — never touching the kernel `Status` column, which stays transport-state-only per AD-11. `TransactionEventHandler` now calls it on both `TransactionCompleted` and `TransactionFailed`; a concurrency exception propagates so the inbox kernel's own retry drives it, rather than being swallowed as "already logged." `InstantPaymentForwardingHandler`'s deferral path now maps to `Deferred` (with its own metric), never `Rejected`. `PaymentsController.ToDuplicateResult` now answers `200` only when the cached payload's status is `Completed` or `Failed`; anything else falls through to the standard `202` duplicate response, matching a fresh row exactly.

**Operational note.** Rows that settled through the deferred/event path *before* this fix have no `ResponsePayload` recorded even though CoreBank genuinely completed them. Existing persistent databases needed a one-time backfill (`UPDATE` the outbox row's `ResponsePayload` from the corresponding `transaction.completed`/`.failed` payload already sitting in the PaymentsAPI inbox) to reconcile pre-fix rows; this is a data migration, not a schema change, and does not recur once the handler records outcomes going forward.

**What is deliberately unchanged.** The wire contract from the Decision above is untouched: still no new response fields, still `200` only for a committed outcome, still `202` for an honest unknown. This addendum closes the last gap in that rule rather than changing it — the gap was that "committed" was only ever being recorded on one of the two paths that can produce it.
