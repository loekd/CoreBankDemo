# ADR-018: Add an opt-in instant-payment rail alongside store-and-forward

**Date:** 2026-09-02
**Status:** Accepted
**Deciders:** Architecture team

## Context

CoreBankDemo models exactly one payment rail: every payment is accepted with `202`, buffered in the payments outbox, and settled by a background processor; CoreBankAPI stores every command in its inbox and executes it on a processor loop. Real SEPA has two rails with materially different engineering constraints — an SCT Inst payment gives the payer's PSP, the payee's PSP, and the clearing mechanism nine seconds in total and runs 24/7/365, while a standard SCT settles in one to two business days in batches. A demo with only the batch shape cannot show a bounded end-to-end budget, an ambiguous timeout on a synchronous hop, or why retry/circuit-breaker/idempotency choices differ between the two rails — the properties that motivate most of the surrounding architecture.

## Decision

Add an opt-in instant rail alongside the existing one; remove nothing.

- **Wire contract (additive only).** `POST /api/payments` gains an optional `scheme` field, closed set `standard` (default) / `instant`. Absent or `standard` reproduces today's behaviour byte-identically. `POST /api/transactions/process` gains an optional `X-Execute-Mode: inline` request header. Absent reproduces today's deferred-execution behaviour exactly.
- **PaymentsAPI** persists and dedupes exactly as today (`PaymentStorageHandler` is untouched — AD-2). For a freshly-stored `scheme=instant` row, a new decorator (`InstantPaymentForwardingHandler`) claims the row through the kernel's per-row claim path (`IOutboxMessageStore<TMessage>.TryClaimByIdAsync`, new — reuses the same `Status`-as-concurrency-token transition `ClaimBatchForPartitionAsync` already uses, so an inline claim and a concurrent background batch claim can never both win the same row), then makes a budgeted, per-attempt-timeout-bounded inline forward via the same validate+submit sequence the background delivery strategy uses (`HttpForwardOutboxDeliveryStrategy` now also implements `ICoreBankTransactionForwarder`, extracted so both callers share one implementation). A committed outcome (CoreBank business success or business rejection) answers `200` and completes the row; a budget/attempt exhaustion, a transport failure, or the row already being claimed releases the claim back to `Pending` (via the existing `MarkAsFailedWithRetryAsync` transport-failure transition) and answers `202` exactly like the standard rail.
- **CoreBankAPI** keeps its inbox unchanged. When `X-Execute-Mode: inline` is present and `TransactionIntakeHandler` stores a brand-new command row, it invokes the same `IInboxMessageHandler<InboxMessage>` (`TransactionExecutionHandler`) the background inbox processor uses, inline within the request — no second execution code path, same atomic ledger/inbox-completion/event-enqueue commit (AD-5). If it throws, the row is left exactly as storage left it (`Pending`) for the processor to drain on its next pass; no partial commit, no event published.
- **New options**, `Payments:InstantRail` (`Enabled` default `true`, `BudgetMilliseconds` default `9000`, `AttemptTimeoutMilliseconds` default `2500`, `MaxAttempts` default `2`), validated at startup (Story 3.1 pattern): every value positive, and `AttemptTimeoutMilliseconds * MaxAttempts` must not exceed `BudgetMilliseconds`.
- **Response semantics extension of AD-11.** AD-11 already treats a business rejection as a successfully processed message (never `Failed`, never retried). This story extends that classification one level up the stack: on the instant rail, PaymentsAPI's `200`-vs-`202` decision is driven by whether CoreBank confirmed a *committed* outcome within budget — success or rejection both commit and both answer `200`; only "no committed outcome observed within budget" (an honest unknown) answers `202`. A budget timeout is therefore never mapped to `504` — the payment may already have executed, and `202`/`Pending` states that truth rather than inviting a client retry that could look like a second payment.
- **Frozen response shapes are not changed.** `PaymentResponse` and `TransactionResponse` carry no new fields; the instant rail communicates its outcome entirely through existing `Status` values (`Completed`/`Failed`/`Pending`) and the HTTP status code. This avoids any change to the checked-in CoreBank OpenAPI document or the generated Kiota client.
- **Metric contract additions.** `corebankdemo.payment.intake` gains a `payment.scheme=standard|instant` attribute on its existing point (no new instrument). A new histogram, `corebankdemo.payment.instant.duration` (`outcome=settled|rejected|deferred`), records once per instant-rail request when the inline attempt concludes or the budget expires.

## Consequences

- The standard rail is provably untouched: `PaymentStorageHandler`, `TransactionExecutionHandler`'s execution logic, and every existing response shape are unchanged; the new behaviour is reached only via the new `scheme`/header opt-ins.
- `IOutboxMessageStore<TMessage>` and `ICoreBankApiClient.ProcessTransactionAsync` gain new members/parameters. Both are additive (a new interface method; a new optional trailing parameter defaulting to today's behaviour), so no existing call site needs to change.
- No change to `LoadTestSupport`, `k6/script.js`, drain semantics, `PartitionCount`, lock lifetime, or claim semantics for the standard rail. The four-store drain and the k6 acceptance gate keep passing unmodified.
- A demo can now show a bounded, honest-uncertainty synchronous hop (the instant rail) side by side with the unbounded, fire-and-forget batch hop (the standard rail) — the pedagogical gap this story exists to close.

## Addendum: Review loop 1 (2026-09-03)

Two review findings, both confirmed against the running code, were resolved without changing the decisions above:

1. **Duplicate replay of a business rejection reported `Completed`.** `OutboxMessage` gains a nullable `ResponsePayload` column (mirrors CoreBank's own `InboxMessage.ResponsePayload`), populated with the serialized `TransactionSubmission` on every completed delivery — `HttpForwardOutboxDeliveryStrategy.ForwardAsync`'s single implementation, used by both the background path (`executeInline: false`) and the instant-rail inline path (`executeInline: true`) — never an instant-only special case. `PaymentsController`'s duplicate-replay path now derives the wire `Status` for a `Completed` row from that payload (`ResolveDeliveredStatus`), not the raw kernel `Status` column, which stays transport-state-only per AD-11 and never distinguishes a business success from a business rejection. The same fix also normalizes a duplicate hitting a still-claimed row (raw `Status = Processing`) to the matrix's documented `Pending` wire word, on the instant rail only — the standard rail's duplicate response is untouched and still surfaces the raw kernel `Status` verbatim, preserving byte-identical baseline behaviour.
2. **CoreBank inline execution could race the background processor into a double ledger execution.** `CoreBankDbContext` was missing `MessageRepositoryBase<InboxMessage, CoreBankDbContext>.ConfigureConcurrencyToken` on `InboxMessage` — `PaymentsDbContext`'s entities already had it, CoreBank's did not — so nothing detected a concurrent write to the same row. `IInboxMessageStore<TMessage>` gains `TryClaimByIdAsync`, mirroring the Payments-side `IOutboxMessageStore<TMessage>.TryClaimByIdAsync` exactly (inherited for free from the shared `MessageRepositoryBase` once the interface member exists). `TransactionIntakeHandler.TryExecuteInlineAsync` now claims the row via this method before ever invoking `TransactionExecutionHandler`; a lost claim falls back to `Accepted`/`Pending`, identical to an already-claimed row on the Payments side. The full CoreBankAPI and Persistence.IntegrationTests suites were re-run afterward (concurrency token is foundational, shared by the background processor) with no regression: 103 and 199 tests respectively, all passing, coverage unchanged at ≥90% line.

Both fixes are additive to the wire/metric contracts recorded above — no field, header, status code, or metric name changed; only a new nullable persistence column, a new kernel interface member (mirroring an existing one), and a missing EF concurrency-token configuration were added.
