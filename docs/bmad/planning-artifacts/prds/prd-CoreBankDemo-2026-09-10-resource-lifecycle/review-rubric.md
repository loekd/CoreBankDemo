# PRD Quality Review — Resource lifecycle and trustworthy recovery reporting

## Overall verdict

This is a well-argued PRD with an unusually strong evidence base: §1.1 pins the diagnosis to five source-of-truth tables and a `pending: 0` consumer group, and the addendum's code references check out against the tree line-for-line. The thesis ("the console is the thing that is broken") is real, the non-goals do genuine work, and the shape — capability spec plus a demo script instead of user journeys — fits a one-operator internal tool exactly.

What is at risk is done-ness. The fix as scoped removes the fingerprint clause from the *event* path, but the same fingerprint gate also sits in the *resource-command* path (`AspireCliAdapter.cs:151`), where it will reject the Start in §4 step 5 — the demo's payoff beat — and neither the PRD nor the addendum's "Surface being changed" mentions it. Two further concrete collisions (the Restart caption duplicating the action button, and a fixed 22-column action rail that the longer captions do not fit) mean an engineer working from §5 alone will build something that does not run the demo in §4.

## Decision-readiness — adequate

The PRD states decisions as decisions. NG2 and NG3 both carry "Considered and declined" with the reasoning attached ("once events stop being discarded there is nothing to catch up"), addendum §C names a rejected alternative *and* an unviable one with the rejection grounds ("the refresh can only fire when `state.Topology` updates, which is exactly the 2s+ debounced path"), and §E justifies raw identifiers over friendly names. The two `[ASSUMPTION]` rows in §8 invite override rather than pretending to be settled — "Flag if you want symmetry instead" is the right register. Nothing here reads as smoothed-to-neutral.

The gap is that the PRD's own biggest execution risk is not in the PRD. Addendum §D ends with "That last point is the main implementation risk in this change and should be an explicit story-level concern" — about `IsCurrent`'s ~10 non-feed callers, several of which use fingerprint sensitivity deliberately for mutation staleness. §5 F1 contains no requirement preserving that behaviour; FR2 covers event rejection only. A decision-maker reading §5 sees a two-clause change with no downside.

The "Verification still owed" row in §8 is honest but toothless: it names a falsifiable prediction and never says what happens if it comes back the other way. Given the §1.1 evidence is independently strong (the sidecar acked the events; the fingerprint mechanism is read straight from code), this is not a blocker — but the row should say whether a contrary result invalidates F1 or merely the narrative.

### Findings
- **high** F1 is silent on the non-feed `IsCurrent` callers (§5 F1, FR1–FR2; risk stated only in addendum §D) — `IsCurrent` has ~10 call sites (`OperatorConsoleController.cs:251, 1052, 1302, 1504, 1553, 1659, 2039, 2192, 2597, 2642`), several deciding whether a *mutation result* still applies. Story creation reads the PRD, and §5 gives it no reason not to blanket-change the predicate. *Fix:* add an FR to F1 — "the staleness check used for mutation results MUST be left unchanged; event attribution gets its own explicitly-named predicate" — and a `[NOTE FOR PM]` naming it as the change's main risk.
- **medium** Verification-owed row has no failure branch (§8, row 4) — "Evidence should show **no** `transaction.completed` rows around 13:38:16" is stated as a confirmation step with no consequence attached either way. *Fix:* add "if the check fails, F1's diagnosis is wrong and the PRD returns to Discovery" (or state plainly that the §1.1 evidence already carries F1 and this is corroboration only).
- **medium** FR14's capability loss is presented as a non-loss (§5 F3, FR15) — "Changing profile is thereafter **Stop AppHost** followed by **Start Regular** / **Start LoadTests**, all of which already exist in the same column." The memlog records this more honestly: "Consequence accepted: … no one-step path." Mid-demo, that is two presses and a full topology restart where there was one. *Fix:* say the cost out loud in FR15 — one-step profile switching is gone, and that was accepted in exchange for row space.

## Substance over theater — strong

Almost nothing here is furniture. There are no personas, no differentiation section, no vision paragraph — all correctly absent for a single-operator internal console, and their absence is a choice the PRD is entitled to make without comment. The NFRs are the tell: NFR2 ("no listening port and no new owned process"), NFR4 ("survive a monochrome terminal and a projector: the words carry the meaning, colour only reinforces it") and NFR5 (coverage extends to the recovery path specifically) are all product-specific constraints someone could fail. None of them is "the system must be reliable."

§1's rhetoric — "It does not. The system works. The console is the thing that is broken." — is earned by the table directly above it, not asserted. The counter-metrics in §7 are the strongest anti-theater signal: C1 and C2 name exactly what the F1 relaxation could break, which is what a counter-metric is for.

### Findings
- **low** NFR1 restates NG1 (§6) — the PRD flags this itself with "*(Restates NG1 as a build-time constraint.)*", so it is self-aware duplication rather than padding, but it is still the one line in §6 that adds no constraint a reader did not already have.

## Strategic coherence — strong

The PRD has a thesis and every part of it serves that thesis. The arc is: the outbox story is the demo's highest-value moment (§1) → the console discards the proof (§1.1) → §4 is the exact six-step script that must work → F1/F2 are what make steps 5 and 6 land. M1 measures precisely the thing the thesis claims is broken ("Currently 0 of *N*"), not activity. The MVP scope kind is problem-solving and the scope logic matches: NG3 refuses to add a staged "recovery moment" on the grounds that fixing the discard is sufficient — that is a thesis being enforced against scope creep, which is rare.

F3 is the weakest tie to the thesis: removing **Switch topology** is an operator preference riding along, justified instrumentally through NFR3 ("buys the room the longer captions need"). That justification does not hold mechanically (see Done-ness), which means F3 currently has no load-bearing connection to F1 or F2 at all.

### Findings
- **medium** F3's only link to the thesis is a claim that does not hold (§5 F3, NFR3) — with the width rationale removed, "remove the Switch button" is an unrelated preference in a PRD that otherwise earns every inclusion. *Fix:* either re-ground it (the real gain is one *vertical* row in the action column, which matters if a caption ever wraps) or state it as an accepted independent ask.

## Done-ness clarity — thin

Several FRs are exemplary. FR4's "with the row held in place — no re-sort, no scroll jump, no change of selection" is directly testable and matches the intent documented at `OperatorConsoleController.cs:2348`. FR9's "at the moment the selection moves — never lagging behind by a poll" states a bound, not an adjective. FR13 and NFR5 are both checkable.

But three requirements collide with the code they will land in, and an engineer will hit all three on day one.

First, FR8 and FR11 fight. FR8 makes the action button's caption condition-derived — "failed or degraded offers **Restart**" — which mirrors `PresentationModel.cs:1289` exactly. FR11 keeps a *separate* always-available restart control that also names its target. For a failed `corebank-api` the action row therefore renders `[Restart corebank-api]` twice, adjacent, doing (presumably) the same thing. The §8 assumption row shows only the healthy case (`[Stop AppHost] [Stop corebank-api] [Restart corebank-api] [Refresh state]`), which is why the collision is invisible in the PRD.

Second, NFR3's remedy is mechanically wrong. `MainWindow.cs:36` fixes `ActionColumnWidth = 22` and `StackButtons` (`:1402`) lays buttons out *vertically* at `Y = startY + index` with `Width = Dim.Fill()` inside that 22-column parent. Removing `_switchButton` frees one **row**, not one column of width. Terminal.Gui renders a button as `[ Text ]`, so 18 characters are usable: `Stop corebank-api` (17) fits, `Start corebank-api` (18) is exactly at the limit, `Restart corebank-api` (20) does not fit, and the longest allow-listed identifier gives `Restart loadtest-support` (24) — six characters over. NFR3 asserts the row "must stay legible … with the longest resource identifier selected" and then points at a fix that does not buy the resource it is spending.

Third, FR10 requires per-selection enablement — "When the selected resource has no legal action, the button MUST be disabled" — but `MainWindow.cs:1554–1555` currently enables on `model.Resources.Any(row => row.CanMutate)`, i.e. *any* resource, not the selected one. Addendum §D says of exactly those lines "enablement already keys off `CanMutate` / `CanRestart` and needs no change." It does need a change, and that mis-read is the kind of thing a story picks up verbatim.

The remaining softness is smaller but real: FR3's "every event the console receives **and can read**" leaves the unreadable case undefined while the next sentence says "An event dropped for any reason MUST NOT vanish silently" — so an unparseable event both must and cannot be recorded. FR6 turns on "because the feed genuinely dropped" without saying how the console distinguishes a genuine drop from the guard-discard it is about to stop doing. M3's "within a few seconds of the measured drain time" is the one metric in §7 without a bound.

### Findings
- **critical** The resource-command path has its own fingerprint gate, and Stop trips it (§4 step 5, §5 F1/F2; `Infrastructure/AspireCliAdapter.cs:151`) — `ExecuteResourceCommandAsync` rejects when `!snapshot.IsFingerprintMatch`, returning "not present in the verified graph." `IsFingerprintMatch` (`AspireJsonParser.cs:25–44`) is false whenever a required resource's replica count differs from `ExpectedReplicaCount` (2 for `corebank-api`) or its expected port is absent — which is exactly the state a Stop creates. **Pressing `Start corebank-api` after `Stop corebank-api` is refused by the adapter**, under either branch (missing resource or replica mismatch). F1 as written only removes the fingerprint clause from `IsCurrent`, so the demo in §4 still breaks at step 5 even after this PRD ships, and G2/G3 are not met. Addendum §D's "Surface being changed" does not list `AspireCliAdapter` at all. *Fix:* add an FR to F1 or F2 — a resource command against an allow-listed resource MUST NOT be rejected because that resource is stopped or mid-restart; the graph check must tolerate the deviation the operator's own Stop created, while keeping the allow-list (C3) and the reachability check. Add `AspireCliAdapter.cs:144–155` to addendum §D.
- **high** FR8 and FR11 both produce `Restart <resource>` for a failed resource (§5 F2) — two adjacent identical captions, and the PRD never says whether they are the same command. *Fix:* decide the split explicitly — either the action button never offers Restart (FR8 drops the failed/degraded case, leaving it to the dedicated control) or the dedicated control goes away and FR8's state machine carries all three actions. Update the §8 layout assumption to show the failed case too.
- **high** NFR3's fix does not buy width (§6 NFR3, FR14; `MainWindow.cs:36`, `:1402`, `:723`) — the action column is a fixed 22 characters and buttons stack vertically; removing Switch frees a row, not a column. `Restart corebank-api` needs 24 of 22, `Restart loadtest-support` needs 28. *Fix:* state the actual budget — 18 usable caption characters at `ActionColumnWidth = 22` — and decide the overflow rule (widen the column, wrap to two lines per NFR3's "no control in use is ever hidden", or truncate the identifier and put the full name in the hint line). Do not leave it to the implementer to discover at render time.
- **medium** FR10 requires per-selection enablement that the addendum says is already handled (§5 FR10; `MainWindow.cs:1554–1555`, addendum §D) — current enablement is `Resources.Any(row => row.CanMutate)`, not the selected row's condition. *Fix:* correct addendum §D's ":1554–1555 … needs no change" and note that FR9 and FR10 together require the buttons to bind to `_resourceList.SelectedItem` changes, which they do not today.
- **medium** FR3's "and can read" leaves the unreadable event undefined (§5 FR3) — the same requirement then says nothing may vanish silently. *Fix:* say what an unparseable event produces — an Evidence row with the raw payload and a parse-failure reason is the obvious answer, and it is what makes "MUST NOT vanish silently" true.
- **medium** FR6 relies on an undefined distinction (§5 FR6) — "because the feed genuinely dropped" needs a stated discriminator now that the guard-discard path is going away. *Fix:* name the condition (subscription gap / sidecar disconnect recorded at the time the row was marked), or restate FR6 as "the fix MUST NOT retroactively resolve rows marked unknown before the subscription recovered."
- **low** M3 has no bound (§7 M3) — "within a few seconds of the measured drain time" against a drain measured at under two seconds. *Fix:* pick a number; "last row resolves within 3s of the final broadcast" is checkable against the §1.1 timestamps.
- **low** FR5 restates FR1 + FR4 (§5 F1) — "MUST NOT report a payment as awaiting settlement when it has already received and acknowledged that payment's settlement broadcast" has no independent testable consequence beyond its neighbours. Harmless as a statement of intent, but it will generate a redundant story. *Fix:* fold it into FR1 or mark it as a restatement the way NFR1 marks itself.
- **low** FR3 vs. the Evidence cap (§5 FR3; `OperatorModels.cs:692`, `OperatorConsoleController.cs:3500`) — Evidence keeps the most recent 500 records. Recording *every* received event, matched or not, moves that ceiling closer during a load-test profile. Not a defect, but "MUST NOT vanish silently" and a rolling 500-record window are in tension worth one sentence.

## Scope honesty — adequate

The non-goals are the best section in the PRD. NG1 draws a hard build-time line around the banking services and NFR1 restates it as a constraint; NG4 explicitly refuses to resurrect the five stranded rows and §8 carries the matching `[NOTE FOR PM]` telling the operator to restart the console before the next demo. That is an omission being owned rather than inferred. Open-items density is low and correctly calibrated — two assumptions, one PM note, one verification item on an internal-tool PRD is nowhere near blocker territory.

What is not explicit is what the fix *does not* cover: the command-path gate above, and the non-feed `IsCurrent` callers. Both are real omissions from the change's surface that a reader of §5 alone would silently assume are handled — precisely the case a `[NON-GOAL for MVP]` or a scope note exists for. The §8 assumption tags are also under-applied: the layout row is tagged, but the claim that Switch removal buys caption room (NFR3) is an inference of the same kind and carries no tag.

### Findings
- **medium** No scope statement on what remains fingerprint-gated (§3, §5 F1) — after F1, the fingerprint still gates resource commands (`AspireCliAdapter.cs:151`), profile preflight, and several mutation-staleness checks. The PRD reads as though the fingerprint clause is being removed, singular. *Fix:* add a line to F1 naming the one check being changed and stating that every other fingerprint use stays — then the critical finding above becomes a visible in-scope decision rather than an omission.

## Downstream usability — adequate

§9 declares this a chain-top PRD ("Consumed by `bmad-architecture` … and `bmad-create-epics-and-stories`"), so traceability matters here. The ID hygiene holds up: G1–G3, NG1–NG4, FR1–FR15, NFR1–NFR5, M1–M3, C1–C3 are all contiguous and unique, and every cross-reference resolves (NG1↔NFR1, FR14↔NFR3, §4↔M2, FR12↔§8). FR2's inline parenthetical — "*(A topology start, stop or switch begins a new run; a resource command does not.)*" — is exactly the right move: it defines the load-bearing term where it is used rather than sending the reader elsewhere.

There is no Glossary, and a few terms would benefit from one. "Terminal state" (G1, FR4, M1) and "settled" (§4 step 6) and "resolves" are used for the same thing; "outcome query" appears once in NG2 ("the existing outcome query already covers genuine ambiguity") and is never defined anywhere in either document, yet it is the reason a whole non-goal stands. "Topology run", "run generation" and "fingerprint" are used in the PRD's reasoning but defined only in the addendum.

The larger downstream concern is the PRD/addendum split. The PRD points at the addendum once ("Mechanism detail, code references and the rejected alternative are in `addendum.md`") — accurate for §A–§C, but §D carries an implementation *risk and a scope warning*, not mechanism. A story-creation pass that reads the PRD and skims the addendum for line numbers will miss it.

### Findings
- **medium** "Outcome query" is load-bearing and undefined (§3 NG2) — it is the sole justification for declining a manual reconcile action, and it appears nowhere else in the PRD or addendum. *Fix:* one clause defining it, or a Glossary entry.
- **low** Terminology drift for the resolved state (§2 G1, §4 step 6, §5 FR4, §7 M1) — "terminal state", "settled", "resolves to settled". Harmless to a human, noisy for story extraction. *Fix:* pick "terminal state" and use it everywhere, with "settled" reserved for the narrative in §1 and §4.
- **low** Addendum §D's risk warning is invisible from the PRD (§9) — the pointer describes the addendum as mechanism and code references. *Fix:* have §9 name §D specifically as containing a scope constraint that stories must honour.

## Shape fit — strong

The shape is right and it looks deliberate. This is a single-operator internal console, and the PRD spends its structure accordingly: no user journeys, no personas, and in their place §4 "The demo this must support" — a six-step script with the one operator as protagonist, which is what a UJ would have been anyway with more ceremony around it. Success metrics are operational (M1 counts rows reaching terminal state; M3 measures console-added lag) rather than user-facing, which matches. Length is proportionate to internal-tool stakes; nothing here is padded to look like a launch document.

Brownfield handling is above average. Existing-code references are carried in the addendum rather than the PRD, and they are accurate — I checked `IsCurrent` at `:3573`, `OnOutcomeEventReceived` at `:2352`, the fingerprint construction in `AspireJsonParser.cs`, `PollInterval` at `OperatorModels.cs:705`, `NextAction` at `PresentationModel.cs:1289`, and all four `MainWindow.cs` button references — every one lands where the addendum says. §D's observation that "the state machine the buttons need exists and is correct — the captions simply never consumed it" is true and is the kind of finding that makes a change cheap.

The two exceptions are the ones already logged above: §D's "needs no change" on the enablement lines is wrong, and `AspireCliAdapter` is missing from the surface list entirely. Both are accuracy defects in an otherwise reliable brownfield map, which is why they are worth naming — a map this good gets trusted.
