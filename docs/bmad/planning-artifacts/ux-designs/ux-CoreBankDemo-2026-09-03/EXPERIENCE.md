> Paired with `DESIGN.md` (same folder). This spine is capability-first: topology, resources, operations, and evidence are the primary information architecture. The named talk journeys in **Key Flows** validate that this IA covers a real 55-minute session end to end — they never define navigation, and the console must answer an unplanned audience question just as well as a rehearsed slide. `mission-critical-talk-v7.json`'s cue track, slide anchors, and linear session are the explicit anti-pattern this spine retires (see **Inspiration & Anti-patterns**); the ports and allow-listed action kinds it defined survive underneath.

## Foundation

Single-surface **Terminal.Gui** desktop console (pinned `2.4.17`, ADR-015), running on the presenter's own laptop, one person, one session, no auth, no network beyond known local HTTP endpoints and a narrowly scoped Aspire child process. No UI system is inherited (Terminal.Gui has none to inherit from); `DESIGN.md` is the visual identity reference, this spine is the behavior. `[ASSUMPTION]` Keyboard and mouse have full parity everywhere — every action reachable by mouse has a documented keyboard equivalent, and single-key shortcuts are the primary path because the operator is frequently mid-sentence; the mouse is a discoverable fallback, not a requirement (Terminal.Gui forbids requiring mouse input in any case). The console references no banking implementation project, opens no Postgres/Redis/Dapr/container socket, and calls only the supported Aspire CLI (`ps`, `describe --format Json`, `resource <name> start|stop|restart`) and known local HTTP endpoints — never Aspire's private dashboard APIs.

**Recovery on relaunch:** the retired cue player's journal/checkpoint/proof-pack machinery has no equivalent here, and this spine makes no claim that one exists. On every launch — including a relaunch after a crash or an intentional close mid-outage — the console rehydrates **only** by re-reading live Aspire (`describe --format Json`/`ps`) and HTTP state; operation/payment history always starts **empty**. Nothing is ever auto-restored from a prior run's local state, journal, or checkpoint — there is no "resume" and no "last known good" claim anywhere in this console. Within a single still-running session, the operator may export the accumulated session history/evidence at any time (Evidence/Results' existing record, not a separate mechanism); that export is never auto-loaded back in on a later launch — it is a manual, explicit action the operator takes if they want a copy of what happened.

## Information Architecture

`[ASSUMPTION]` The primary layout is one persistent cockpit shell with a small number of switchable workspaces — never a wizard, a queue, or a deep tree — because the operator must reach any capability in seconds while talking, and hunting through nested menus is a stage failure (brief §3, §7).

**Persistent shell chrome** (always visible, in every workspace):

| Element | Contents | Purpose |
|---|---|---|
| Topology bar (top, thin) | Current AppHost (Regular / LoadTests), Owned/Attached badge, persistent DevProxy on/off chip, live resource status-chip strip, quick-open cluster (Aspire dashboard / Jaeger / metrics view) | Continuous system confidence, kept as a thin top context/status bar rather than a boxed panel, and one-keystroke access to the dashboards this console deliberately does not reimplement (brief §4 Environment, §8) |
| Navigation rail (left, compact) | Operations · Resources · Evidence/Results · Load Test, one row per workspace | Shallow switching — one keypress (`1`–`4`) or click, never nested; replaces a horizontal tab bar so the workspace content beside it reads as one continuous surface instead of stacked cockpit panels |
| Evidence strip (bottom) | Last action's one-line truthful outcome (status/latency/timestamp) + Details | "What just happened" always visible without leaving the current workspace |
| Key legend (bottom-most row) | Context-sensitive shortcut hints | Discoverability without hunting |

**Switchable workspaces:**

| Workspace | Reached from | Purpose | Capabilities it hosts |
|---|---|---|---|
| Operations | Nav rail / `1` | Submit and query payments | Standard/instant payment form, presets, idempotency mode, resend-same-key, bounded burst, outcome query |
| Resources | Nav rail / `2` | Control the running topology | Start/attach/stop/switch AppHost, per-resource start/stop/restart, DevProxy on/off, replica count + scale-if-supported |
| Evidence/Results | Nav rail / `3` | Inspect what happened in depth | Full response detail (code/latency/body), inbox/outbox contents, balance/conservation, action history |
| Load Test | Nav rail / `4` | Run and read the accepted mixed-rail workflow | Reset→Run→Wait→Assert→Investigate phases (Reset is Run's own first internal phase, not a standalone control), five invariants, inline-instant-settlement proof |

No workspace is more than one keypress from any other; none contains a nested sub-navigation. A workspace that needs a topology it doesn't currently have (for example, Load Test needs the LoadTests AppHost) shows why it's unavailable and a one-step switch action, rather than hiding itself or silently degrading — this keeps the IA shallow even across the two-topology constraint.

**Main workspace composition** (Operations, Resources, Evidence/Results, Load Test content areas): each reads as one operational activity surface, not a cockpit panel. Content is a list of `DESIGN.md` **Activity rows** — a bold verb/object headline ("Stop — corebank-api", "Submit — standard payment") with the exact command/request detail muted directly beneath it, and a truthful status marker held in a fixed-width left gutter, never inline-mixed with the headline. Each workspace's one primary action (and, in Resources, the selected row's contextual action) anchors in a fixed lower action/detail region at the bottom of that content, directly above the persistent Evidence strip — so the eye's path is always rows above, action fixed below, outcome fixed below that, with no boxed sub-panel breaking the flow.

No mockup/wireframe of this console itself is rendered for this pass (spine-only; task scope excludes mockups/wireframes). **Spine wins on conflict.**

## Voice and Tone

Microcopy. Brand voice/posture lives in `DESIGN.md` Brand & Style. The console narrates truth the operator will read aloud on stage (brief §6 "Latency honesty," "Truthfulness on failure") — plain, factual, and status-vocabulary-exact.

| Do | Don't |
|---|---|
| `202 Pending — no committed outcome yet` | `Something went wrong, please wait...` |
| `Ambiguous — not yet reconciled; Resend is unsafe; a fresh submission or an outcome query is the only way forward` | `Retrying...` (implying it is safe when it is not) |
| `Attached — this AppHost is not owned by this session` | `Connected` (hides the ownership distinction that gates Stop) |
| `Restart CoreBank API? This will interrupt in-flight work.` | `Are you sure?` |
| `5 invariants: 4 passed, 1 failed — Instant inline-settlement: 0 observed` | `Load test failed` |
| Exact HTTP status codes and field names, always | Paraphrased or rounded evidence |

## Component Patterns

Behavioral. Visual specs live in `DESIGN.md.Components`.

| Component | Use | Behavioral rules |
|---|---|---|
| Topology bar | Persistent shell | Read-only display; commanded transitions (a resource/AppHost action the operator just triggered) flip that chip to `Running`/`~` immediately on dispatch, before the next poll; externally observed changes instead poll at most once every 1–2 seconds and must hold the new state for one full interval before the chip updates, so a flapping dependency reads as "unstable," not as flicker; clicking a status chip opens resource detail in the Resources workspace, never mutates directly; renders as a thin top context/status bar on the same `surface-base` tone as the workspace beneath it, not a boxed panel; each chip (including the persistent DevProxy chip) is individually keyboard-focusable, not one opaque region (see Accessibility Floor) |
| Navigation rail | Persistent shell | Compact, fixed-width left column listing the four workspaces; one keypress (`1`–`4`) or click activates a workspace; active item highlighted with `accent-navy`; never hidden, never collapsed into a horizontal tab strip, never nested; shrinks to icon+shortcut only below the preferred terminal width, labels hidden but switching stays one key |
| Status chip | Topology bar, Resources, and every Activity/Resource row's status gutter | Read-only; symbol + label + color together, never color alone; four resource states (`Healthy`/`Running`/`Unknown`/`Failed`) plus the independent DevProxy on/off chip; `Unknown` (stale/unparseable Aspire snapshot) is worded distinctly from `Unreachable` (the console itself cannot reach the resource's HTTP/Aspire endpoint — a transport failure on DemoRunner's own side, not a claim about the resource); both disable that resource's mutating commands until a fresh read succeeds |
| Activity row | Every workspace's main content | Bold verb/object headline, muted command/request detail directly beneath it, and a status marker in a fixed-width left gutter; rows sit directly on the continuous work surface, borderless, so the list reads as one operational activity surface rather than stacked cards (see `DESIGN.md` Activity row); before any row exists yet, shows one muted placeholder row stating the workspace has no activity this session — never a blank void |
| Resource row | Resources workspace | An **Activity row** whose fixed action slot shows the single legal next command (Start/Stop/Restart) for that resource; the slot's position never moves when the label changes, so the recovery action for a stopped resource lands exactly where the stop action was; during a commanded transition, the row shows an elapsed-time readout ("Restarting — 4s") in its meta line rather than a bare spinner, per the same latency-honesty rule as the Load phase strip's Wait phase |
| AppHost control panel | Resources workspace | Start / Attach / Stop / Switch for Regular and LoadTests, each with the same elapsed-time-while-transitioning treatment as a Resource row. Whole-AppHost Stop **and** Switch are both disabled (visibly, not hidden) whenever the current topology is Attached — Switch is a compound stop-then-start and cannot proceed on a topology that this session doesn't own any more than a plain Stop can. On an Attached topology, allow-listed, fingerprint-verified, individually confirmed per-resource Start/Stop/Restart commands remain permitted — ownership (whole-AppHost) and resource control are tracked and gated independently, as codified by amended `ADR-015`. Switch is classified destructive and gated by the **Confirmation modal** exactly like Stop |
| Payment form | Operations workspace | `[ASSUMPTION]` Preset pair of demo accounts editable inline; amount and rail (`standard`/`instant`) are explicit fields, never file edits; submit is the single primary action in this workspace, anchored in its fixed lower action/detail region |
| Idempotency selector | Operations workspace, part of payment form | `[ASSUMPTION]` Three explicit modes — Generated (default), Supplied, Omitted; Omitted is visibly labeled "not retry-safe after an ambiguous outcome" before submission, not after |
| Resend-same-key action | Operations workspace, appears after a Generated/Supplied submission | `[ASSUMPTION]` First-class button, not a hidden re-submit; disabled entirely (not just discouraged) after an Omitted-key submission that resolved ambiguously |
| Burst control | Operations workspace | Bounded count field (enforced min/max), shows accepted/completed/failed running totals live. Its **Cancel** control is the one control in the entire console explicitly exempt from the global single-action-in-flight lock (see State Patterns) — it stays enabled for the full duration of the burst it belongs to and cancels without discarding evidence already captured; every other mutating control everywhere else stays disabled until the burst resolves or is cancelled |
| Outcome query | Operations workspace | Look up a submitted payment/transaction by its captured id or key; always available, read-only, never blocked by the single-action-in-flight rule — visually identical whether or not another action is in flight |
| DevProxy toggle | Resources workspace | On/off only; never edits checked-in proxy configuration; shown as unavailable (not hidden) when the current topology doesn't support it; its state is mirrored live as a persistent chip in the topology bar, visible from every workspace, so leaving Resources never hides that faults are still being injected |
| Replica indicator | Resources workspace | Always shows the current count; the scale control itself is present only when the supported Aspire command surface actually allows scaling for that resource — otherwise it's a read-only figure, never a disabled-looking button that implies it should work |
| Load phase strip | Load Test workspace | Renders `Reset → Run → Wait → Assert → Investigate` exactly as the accepted workflow defines it; Reset is Run's own first internal phase — there is no standalone, generic Reset control anywhere in the console, and every rerun (including Journey B's repeated reruns across planted-bug branches) resets the disposable topology again through this same accepted sequence, never a shortcut around it; no second, DemoRunner-invented assertion path. Before any run this session, all five phases show `not-yet-reached` |
| Invariant chip | Load Test workspace | One chip per invariant (exactly-once, no-loss, balance-conserved, ordering, drained) plus a distinct inline-instant-settlement chip; each shows pass/fail/not-yet-observed individually — never collapsed into one pass/fail bit; before any run this session, all chips show `not-yet-observed` |
| Primary action button | Every workspace's fixed lower action/detail region | Exactly one per workspace, Enter/click fires it; when that workspace's primary action is itself destructive (Load Test's **Run**, because Reset truncates the disposable topology's stores as its first phase), it renders and behaves as a **Destructive action button** instead, gated by the **Confirmation modal** every time Run fires, including Journey B's repeated reruns |
| Destructive action button | Resource Stop/Restart, AppHost Stop/Switch, Load Test Run | Fires only after the **Confirmation modal** is answered with its typed key; its resolved/inverse action always renders in the exact screen slot the original occupied (Stop → Restart in the same resource-row slot) |
| Evidence strip | Persistent shell | Shows the single most recent action's truthful one-line outcome, labeled with the topology/profile and run generation it was captured against (see State Patterns, Evidence provenance); never itself scrolls; "Details" opens the full record in Evidence/Results; before any action this session, shows a muted "No actions yet this session" placeholder |
| Confirmation modal | Any destructive Resources/Load-Test-Run action (resource Stop/Restart, AppHost Stop/Switch, Load Test Run) | Names the exact target and exact command; opens with focus on **Cancel** (the safer default) and traps focus entirely while open — nothing else on screen is reachable; the single explicit confirmation key is `Y`; `Escape` cancels; on either outcome, focus returns to the exact control that opened it. No hold-to-confirm gesture and no double-Enter confirmation exist anywhere in this console |

## State Patterns

| State | Surface | Treatment |
|---|---|---|
| Owned vs Attached AppHost | Topology bar, Resources workspace | Explicit badge, never inferred; Attached disables the whole-AppHost Stop **and** Switch controls (visibly, not hidden) but still permits allow-listed, fingerprint-verified, per-action-confirmed resource-level commands — ownership and resource control are tracked and gated independently, as codified by amended `ADR-015` |
| Resource: Unknown | Topology bar / Resources | Stale or unparseable Aspire snapshot; shown as `state-neutral`/`○` labeled `Unknown`, all mutating commands on that resource disabled until a fresh read succeeds |
| Resource: Unreachable (transport failure) | Topology bar / Resources | The console's own HTTP/Aspire-CLI call to check this resource failed — distinct from `Unknown`'s stale-snapshot meaning and distinct from Aspire itself reporting the resource stopped; shown as `state-neutral`/`○` labeled `Unreachable`, with the meta line naming the specific failed call; all mutating commands on that resource disabled until a fresh read succeeds |
| Resource: Healthy / Running / Failed | Topology bar / Resources | `state-healthy`/`●`, `state-running`/`~`, `state-failed`/`✕` respectively, always text+symbol, never color-only |
| Resource/AppHost transitioning (Start/Stop/Restart/Attach/Switch) | Resources workspace, AppHost control panel | Extends latency honesty beyond Load Test: show `state-running`/`~` immediately and re-enable mutations only after Aspire confirms resolution. See Component Patterns, Resource row and AppHost control panel |
| Payment: Pending | Operations / Evidence | `202`, amber, labeled `Pending` — genuinely unresolved, background delivery continues |
| Payment: Ambiguous | Operations / Evidence | An Omitted-key request whose outcome could not be reconciled; amber, labeled `Ambiguous — not yet reconciled`, Resend disabled; only a fresh submission or an outcome query can move it forward, without implying the outcome is permanently unresolvable |
| Payment: Completed / Failed | Operations / Evidence | `200`, green (`Completed`, business success) or the failure reason rendered plainly (`Failed`, business rejection) — both are *proven* outcomes and both are distinct from `Pending` |
| Single action in flight | Global, all workspaces | Starting any mutating action anywhere disables every other mutating control console-wide until it resolves. Exactly two categories stay available throughout: (1) read-only inspection — outcome query, evidence detail, topology bar reads; (2) the in-flight action's **own** Cancel control where one exists (currently only the Burst control's Cancel) — it is the one control exempt from the lock it itself holds, so a running burst can always be stopped |
| Destructive confirmation pending | Resources / Load Test | Modal open with focus on **Cancel**, nothing else interactive; the explicit confirmation key is `Y`, `Escape` cancels; either outcome returns focus to the exact control that opened the modal, with no side effect on cancel |
| Load workflow: Reset/Run/Wait/Assert/Investigate | Load Test | Reset is Run's own first internal phase, never a separate control; every rerun repeats the full sequence from Reset, so stale data from a prior run can never be mistaken for a genuine planted-bug regression. Each phase is a first-class state, not a spinner; a stalled Wait phase after its expected drain window looks distinctly "still waiting, not hung" via an elapsed-time readout, never a bare spinner (brief §6 "Latency honesty") |
| Workspace unavailable for current topology | Load Test (needs LoadTests AppHost) | Visibly disabled with the reason and a one-step switch action, never hidden |
| Workspace: cold / before first action this session | Operations, Evidence/Results, Load Test | Operations: payment form and burst control are fully usable immediately, the activity list shows one muted "No payments submitted this session" row, burst totals read 0/0/0; Evidence/Results: one muted "No actions yet this session" row, no stale prior-session data ever appears (see Foundation, Recovery on relaunch); Load Test: all five phase-strip cells and all invariant/inline-instant-settlement chips show `not-yet-reached`/`not-yet-observed`, Run is enabled |
| Evidence provenance across a topology switch | Evidence/Results | Every evidence record carries the topology/profile (Regular/LoadTests) and a run-generation label it was captured under; switching topologies never deletes prior evidence, but every record from before the switch is visibly, unmistakably marked with its old topology/generation — a presenter glancing back can never mistake stale Regular-topology evidence for current LoadTests evidence or vice versa. Switch itself is a compound destructive action (stop-then-start) and is gated by the same Confirmation modal as a plain Stop |
| DevProxy on/off | Topology bar (all workspaces), Resources | Persistent chip in the topology bar mirrors the Resources-workspace toggle live, visible regardless of which workspace is active, so induced faults are never silently forgotten after leaving Resources |

## Interaction Primitives

- **Single keypress per workspace switch** (`1`–`4` or equivalent), mouse click on the navigation rail as the discoverable fallback. `[ASSUMPTION]` keyboard and mouse are full peers everywhere, not keyboard-first-with-mouse-afterthought or the reverse — both are optimized, because the brief leaves this open and the fast path assumes parity rather than blocking on it.
- **One primary action per screen**, always in the same position, anchored in the workspace's fixed lower action/detail region (`DESIGN.md` primary-action-button). Enter/click both fire it.
- **Single action in flight, globally, with exactly one named exception.** Duplicate activation (double-click, repeated Enter) is debounced to exactly one dispatch; every other mutating control shows disabled/busy, not merely unresponsive — except the in-flight action's own Cancel control (currently only Burst control's Cancel), which stays enabled for the duration of the action it cancels (see State Patterns, Single action in flight).
- **No automatic retry after an ambiguous Omitted-key mutation.** The console never re-sends on the operator's behalf; Resend-same-key is offered only when the original key is known safe to reuse (Generated/Supplied).
- **Resend-same-key is first-class**, not a hidden re-submit — it is a named, always-visible action once a Generated/Supplied submission exists that can be resent.
- **Destructive actions require the single explicit typed confirmation key `Y`** in the Confirmation modal — no hold-to-confirm gesture and no double-Enter confirmation exist anywhere in this console (a held key's OS/terminal-dependent auto-repeat is not a reliable or testable substitute for a real confirmation, and Terminal.Gui has no "key held for N ms" primitive to build one from); a stray keypress on stage must never fire a stop/restart/switch/load-run by itself. Applies to: resource Stop/Restart, AppHost Stop/Switch, and Load Test Run.
- `[ASSUMPTION]` **The inverse recovery action always occupies the same screen position as the action that necessitated it** (Stop → Restart in the same resource-row slot) — recoverability is a location guarantee, not just a feature's existence.
- **Raw evidence is available on demand**, never forced onto the default view: the evidence strip is a truthful one-liner; "Details" expands the same record's full body/log without paraphrasing it. The expanded view is pannable and optionally wrap-toggled (see Responsive & Platform).
- **Reset is Run's own first internal phase for the disposable LoadTests topology** (`Reset → Run → Wait → Assert → Investigate`), never a standalone control; every rerun of the accepted workflow resets the disposable topology again through this same sequence. The Regular topology has no generic "reset to a known state" action of any kind — matching the brief's open question, resolved toward "no blanket reset on the main topology."
- **Banned:** a linear/next-only cue queue, slide anchors or speaker notes as a navigation dependency, auto-advance past unproven evidence, auto-retry of an ambiguous keyless payment, any generic/arbitrary command execution, direct store/broker access, treating elapsed time alone as a proxy for success, hold-to-confirm/double-Enter as a confirmation mechanism, and any local journal/checkpoint claim that a prior session's state was restored on relaunch.

## Accessibility Floor

Behavioral; visual contrast lives in `DESIGN.md`.

- Full keyboard operability for every action Terminal.Gui exposes to the mouse — Tab/arrow/Enter/shortcut keys reach everything (mouse is never a hard requirement, per ADR-015/Terminal.Gui norms).
- Every state is encoded in text **and** a fixed symbol, never color alone (`DESIGN.md` Colors) — this is the floor for color-vision-deficient operators and for any terminal degraded to 16 colors or monochrome.
- Focus is always visibly indicated (reverse-video per `DESIGN.md`), and the literal Tab order per workspace is: **topology bar** (resource chip 1…chip N in strip order, then DevProxy chip, then quick-open control 1…M) → **navigation rail** (item 1…4) → **active workspace content** (row 1…N top-to-bottom, then that workspace's primary/contextual action) → **evidence strip** (Details). `Shift+Tab` reverses the same order exactly. There is no wrap: Tab from the evidence strip's Details does not cycle back to the topology bar, and `Shift+Tab` from the topology bar's first chip does not cycle to the evidence strip — an operator who tabs past either end simply stays at that end. The confirmation modal, while open, traps focus entirely inside itself (opens with **Cancel** focused; `Y` confirms, `Escape` cancels; focus returns to the exact control that opened it on either outcome) and is the one place Tab order is fully self-contained rather than shell-wide.
- No content-bearing information is conveyed by text size or weight alone — bold/dim are used for emphasis, never as the only signal of a distinct meaning.
- Terminal screen-reader support is not claimed by this spine; accessibility here means keyboard operability and color-independent state, not screen-reader compatibility, which is out of scope for a Terminal.Gui console per the brief's stated non-goals.

## Inspiration & Anti-patterns

- **Lifted (composition only) from [`imports/operator-console-inspiration.png`](imports/operator-console-inspiration.png)**, a user-supplied operator-console composition reference (`.memlog.md` decision) — the transferable principles are: a single near-black work surface, strong verb/object hierarchy, muted command/request detail, simple top-bar controls, and a fixed lower action/detail region. **Rejected explicitly:** its branding, exact colors, labels, and top-tab navigation; this spine uses a compact left rail so workspace switching remains visible without consuming the horizontal status bar. Where the reference and this spine's stated requirements conflict, the spine (this file and `DESIGN.md`) wins. (This is this principle list's one stated home; `DESIGN.md` Brand & Style and this file's Information Architecture cross-reference here rather than restating it.)
- **Rejected — the retired cue player (`mission-critical-talk-v7.json`, `TalkCueDefinition`, `SessionController`'s linear cue track), including its journal/checkpoint/proof-pack recovery machinery.** `SlideAnchor`, `SpeakerNote`, a fixed `Next`-gated sequence, and an append-only journal with a `REHEARSAL`-labeled last-known-good proof pack coupled the tool to one deck version and one recovery model; every deck revision made the tool stale. This spine replaces that with capability-driven workspaces the two talks *use*, never *define*, and with a deliberately simpler recovery contract: rehydrate live Aspire/HTTP state only, start every relaunch with empty operation history, never auto-restore a prior run's local state (see Foundation, Recovery on relaunch). The underlying ports (`IProcessAdapter`, `IHealthMonitor`, `IHttpActionExecutor`, `ILoadWorkflowRunner`, `IBrowserLauncher`, `IJournal`, `IProofPackStore`) and the allow-listed `ActionKind` set survive underneath this new IA — only the presentation/navigation layer and the checkpoint-resume model are retired.
- **Lifted from the Aspire dashboard's resource confidence pattern** — a continuously-refreshed status-chip strip — but reimplemented over the supported `aspire describe --format Json`/`ps` CLI rather than Aspire's private dashboard APIs (ADR-015's explicit boundary).
- **Lifted from the accepted Reset→Run→Wait→Assert→Investigate load-workflow phase strip** (Story 7.1/7.3, spec-add-instant-rail-load-coverage) — reused as-is in the Load Test workspace, not reinvented as a second assertion path.
- **Rejected — a wizard or wizard-like linear onboarding for payment submission.** Presets fill the form immediately; typed override is available but never mandatory, because the operator must be able to fire a payment in seconds mid-sentence.
- **Rejected — a "successful" color/state implied by elapsed time or silence.** Every state above is a first-class typed result; a nine-second instant-rail attempt, and every Resource/AppHost transition, must visibly still be working, not look hung (brief §6).
- **Rejected — reimplementing the Aspire dashboard, Jaeger, or the metrics view inside the console.** These are opened, not rebuilt (brief §9 non-goals); the quick-open cluster in the topology bar is the entire surface for them.

## Key Flows

### Flow 1 — Climax: outage and durable recovery (Loek, mid-talk, either session — the canonical capability sequence)

This exact sequence is the one both named journeys below pass through at their own moment, and the one an operator would replay unscripted if an audience question demanded it — it is described here in capability terms, not slide numbers, precisely because it belongs to no single talk.

1. Loek is in the **Resources** workspace. He selects the `corebank-api` resource row and chooses **Stop**; the confirmation modal names the exact resource and command, opens with **Cancel** focused; he presses `Y` to confirm.
