> Paired with `DESIGN.md` (same folder). This spine is capability-first: topology, resources, operations, evidence, and induced faults are the primary information architecture. The named talk journeys in **Key Flows** validate that this IA covers a real 55-minute session end to end — they never define navigation, and the console must answer an unplanned audience question just as well as a rehearsed slide. `mission-critical-talk-v7.json`'s cue track, slide anchors, and linear session are the explicit anti-pattern this spine retires (see **Inspiration & Anti-patterns**); the ports and allow-listed action kinds it defined survive underneath.

## Foundation

Single-surface **Terminal.Gui** desktop console (pinned `2.4.17`, ADR-015), running on the presenter's own laptop, one person, one session, no auth, no network beyond known local HTTP endpoints and a narrowly scoped Aspire child process. No UI system is inherited (Terminal.Gui has none to inherit from); `DESIGN.md` is the visual identity reference, this spine is the behavior. The console renders in one of **two palettes** — the default dark cockpit surface and a light surface for projector work — chosen with `--light`/`--dark`, with `COREBANK_DEMO_THEME`, or live with `T`. The palettes differ in token values only (`DESIGN.md` Colors, Light mode); no surface, state, symbol, flow, or shortcut in this spine varies by palette, and nothing below should ever be written so that it does. `[ASSUMPTION]` Keyboard and mouse have full parity everywhere — every action reachable by mouse has a documented keyboard equivalent, and single-key shortcuts are the primary path because the operator is frequently mid-sentence; the mouse is a discoverable fallback, not a requirement (Terminal.Gui forbids requiring mouse input in any case). The console references no banking implementation project and opens no Postgres, Redis, or container-engine socket. It calls the supported Aspire CLI (`ps`, `describe --format Json`, `resource <name> start|stop|restart`) and known local HTTP endpoints — never Aspire's private dashboard APIs — and reaches the message broker only through a Dapr sidecar of its own (see **Outcome-feedback boundary**), never the broker directly.

**Fault-injection boundary.** The console changes the conditions the system runs under by writing a **generated session configuration** that Dev Proxy watches and reloads on its own. Three boundaries are absolute. First, it **never writes a checked-in Dev Proxy configuration file** — `CoreBankDemo.AppHost/devproxy/config/devproxyrc.json`, its `devproxy-errors.json`, and `CoreBankDemo.LoadTests/devproxy/config/devproxyrc-latency.json` are read-only inputs that supply the named presets, so a demo can never dirty the working tree and the LoadTests band tuned to overrun the instant rail's budget is always one preset chip away, intact. `[ASSUMPTION]` The generated session config lives at a gitignored path alongside the profile it belongs to; the exact location is an architecture decision, and the only requirement this spine makes is that it is generated, per-session, and ignored by git. Second, it injects faults **only** through Dev Proxy's own plugins — it never modifies application configuration, never introduces a fault path into the banking services themselves, and cannot inject a fault the proxy could not already produce. Third, arming is a launch-time property: `Features:UseDevProxy` is read when the AppHost starts, so the console decides arming when it starts a topology and can only report — never change — the armed state of a topology already running, including any topology it merely Attached to.

`[ASSUMPTION]` Dev Proxy's REST API (`127.0.0.1:8897`) exposes proxy status, recording, and stop, but no plugin-configuration mutation, so the watched-file reload is the only mechanism available for changing levels live. If a future Dev Proxy version exposes direct level mutation, the staged-then-Apply interaction and the applied-versus-observed distinction both survive unchanged — only the write mechanism behind Apply would differ.

**Outcome-feedback boundary.** The console **listens** to the outcome CoreBank already broadcasts, so a submitted payment resolves on its own instead of sitting at `202 Pending` until the operator remembers to run an outcome query. **Four** CloudEvent types on the `transaction-events` topic are the entire contract — three of them until the cancel capability landed in this pass, which makes `com.corebank.transaction.cancelled` a full member alongside the others rather than a special case of failure — and the console renders each distinctly rather than flattening them into one generic "processed" signal:

| CloudEvent type | Fields the console renders | What it proves |
|---|---|---|
| `com.corebank.transaction.completed` | `TransactionId`, `Status`, `ProcessedAt` | The payment reached a committed successful outcome |
| `com.corebank.transaction.failed` | `TransactionId`, `Status`, `ProcessedAt`, `ErrorReason` | The payment was rejected — a proven business outcome, not a transport error |
| `com.corebank.account.balance.updated` | `TransactionId`, `AccountNumber`, `Delta`, `NewBalance`, `Currency` | Money actually moved on a specific account, by a specific amount |
| `com.corebank.transaction.cancelled` | `TransactionId`, `Status`, `ProcessedAt`, `Reason` | The payment was withdrawn before it executed — a proven outcome in which no money moved, and the only outcome that is safe to retry under a new key |

A successful transaction therefore produces **three** events (one `completed` and two `balance.updated`, debit then credit), a rejected one produces **one** (`failed`, with no balance events), and a cancellation that beat execution produces **one** (`cancelled`, with no balance events either — nothing moved, so there is nothing to report). The console's renderings are built on those exact counts rather than on a guess about them.

**The submission's own answer is the other half of the vocabulary, and one of its codes changed under this spine.** A standard payment answers `202 Pending` — acknowledged, no committed outcome yet, background delivery continues. An instant payment answers `200` with the outcome it actually committed inside its budget, or **`504` with `Status: Cancelled`** when the budget expired *and* the withdrawal was proven: the rail's own time-out withdrawal, in which nothing executed, the same key replays the same answer, and a retry under a new key is safe. That `504` is a **proven** outcome, ranked with `200 Completed` and `200 Failed` and never rendered as a transport failure — while a `504` whose body does not say `Cancelled` is an ordinary gateway failure and is rendered as exactly that, because the code alone proves nothing and the body is what carries the business meaning. The instant rail's `202` survives only for the case the rail could not settle *and* could not prove the withdrawal either way, which is the one budget-exhaustion answer that leaves a payment open. This overrides an earlier reading of this spine in which `202 Pending` was the only answer a budget-exhausted instant payment could produce; that reading predates the rail's cancel-on-exhaustion behaviour, and the Key Flow beats written against it are corrected below.

Four boundaries are absolute. First, **observation must never alter what is observed.** The console is a read-only listener and must never become a competing consumer that diverts an event away from PaymentsAPI — a feedback loop that stole the deliveries it was built to display would break the very system the talk is proving, and would do it invisibly. Second, the console **correlates only by `TransactionId`**, which every one of the submission's own answers returns (`PaymentsController` sets the `Accepted` location and body from `snapshot.TransactionId`, and the `200` and `504` bodies carry the same id) and which all four events carry; no new correlation identifier, header, or side channel is introduced into the banking services for this console's benefit. **The id is the idempotency key.** `PaymentStorageHandler` computes `var key = idempotencyKey ?? Guid.NewGuid()` and sets `IdempotencyKey` and `TransactionId` to that same value, so in **Generated** and **Supplied** modes the console holds the payment's identifier *before* it sends the request and correlation does not depend on the response arriving at all. This overrides an earlier reading in this file that treated the id as a server-generated value the console could not know until the answer came back; two rules follow from the correction and are stated where they apply — a submission whose response never arrives is still trackable (State Patterns, *Payment: no response*), and **Cancel payment** is live for the whole of an instant payment's budget window rather than only after it resolves (Component Patterns, *Cancel payment action*). In **Omitted** mode alone there is no key and therefore no id until the bank answers; that is a further consequence of the mode already labelled "not retry-safe after an ambiguous outcome", not a separate limitation, and it is stated in those terms wherever it bites. Third, it **subscribes to `transaction-events` directly, through a Dapr sidecar of its own** — launched and owned as a child process exactly as the console already launches an Aspire AppHost. Nothing is added to any banking service for the console's benefit: no new endpoint, no relay, no contract change. That matters beyond tidiness, because a demo tool that required the demonstrated system to be modified for its benefit would be demonstrating the tool. Owning the sidecar also means the feed works identically on Regular, on LoadTests, and on a topology the console merely **Attached** to, none of which have to expose anything for it. The subscription is a **streaming** one (`Dapr.Messaging`): the console dials out to its own sidecar over gRPC and receives messages on that stream, so it still hosts no inbound listener and still opens no port. Its **own app-id gives it its own consumer group**, and that is precisely what preserves the first boundary — PaymentsAPI's `payments-api`-scoped subscription keeps receiving every event, and the console's copy is a fan-out, never a diversion. The console takes a package reference to the Dapr messaging client and declares the four event contracts as local wire types, holding **no project reference** to any banking implementation project, so ADR-015's machine-checkable graph invariant is unchanged. The standing requirements remain: read-only, prompt enough that a settled payment appears while the operator is still describing it, liveness observable to the console so a payment row can state whether anyone is listening for its outcome, and no change whatsoever to how PaymentsAPI receives the same events. Fourth, the console **never synthesises an event it did not receive** — no inferred settlement, no optimistic completion, no timeout-becomes-failure.

**Recovery on relaunch:** the retired cue player's journal/checkpoint/proof-pack machinery has no equivalent here, and this spine makes no claim that one exists. On every launch — including a relaunch after a crash or an intentional close mid-outage — the console rehydrates **only** by re-reading live Aspire (`describe --format Json`/`ps`) and HTTP state; operation/payment history always starts **empty**. Nothing is ever auto-restored from a prior run's local state, journal, or checkpoint — there is no "resume" and no "last known good" claim anywhere in this console. Within a single still-running session, the operator may export the accumulated session history/evidence at any time (Evidence/Results' existing record, not a separate mechanism); that export is never auto-loaded back in on a later launch — it is a manual, explicit action the operator takes if they want a copy of what happened.

The outcome feed obeys the same rule and states it out loud: **the console never replays broadcast history on connect.** The feed begins at the moment the subscription is established and stamps that time in its header (`Listening since 12:01:04 — events before this time were not observed`), so an empty feed after a relaunch can never be read as "nothing has settled." Events that CoreBank broadcast while this console was not listening are gone from its view, and the console says so rather than implying it saw a quiet system.

## Information Architecture

`[ASSUMPTION]` The primary layout is one persistent cockpit shell with a small number of switchable workspaces — never a wizard, a queue, or a deep tree — because the operator must reach any capability in seconds while talking, and hunting through nested menus is a stage failure (brief §3, §7).

**Persistent shell chrome** (always visible, in every workspace):

| Element | Contents | Purpose |
|---|---|---|
| Topology bar (top, thin) | Current AppHost (Regular / LoadTests), Owned/Attached badge, persistent fault chip (Dev Proxy arming + whether faults are in force), live resource status-chip strip, quick-open cluster (Aspire dashboard / Jaeger / metrics view) | Continuous system confidence, kept as a thin top context/status bar rather than a boxed panel, and one-keystroke access to the dashboards this console deliberately does not reimplement (brief §4 Environment, §8) |
| Navigation rail (left, compact) | Operations · Resources · Evidence/Results · Load Test · Faults, one row per workspace | Shallow switching — one keypress (`1`–`5`) or click, never nested; replaces a horizontal tab bar so the workspace content beside it reads as one continuous surface instead of stacked cockpit panels |
| Transient announcement (foot of the content area) | A failed or refused command's one truthful line, then nothing | The only non-persistent element in this table, listed here because it inherited the removed bottom band's job without inheriting its rows: a refusal appears at the foot of whichever workspace is active, where the operator is already looking. Why the band went, and why nothing truthful goes with it, is argued once immediately below |

**Override — the bottom band is removed from every workspace.** This table carried two more rows until this pass: a persistent **Evidence strip** and a **Key legend**. Both are gone, together with the in-flight action line between them — three rows of permanent chrome in a shell that was already spending ten of its thirty rows before any content appeared, while Operations' payment area got four (brief §4). The removal is deliberately uniform across all five workspaces, so the shell stays one shape rather than becoming Operations-shaped. Nothing truthful is lost by it, because the strip was never the record — **Evidence/Results** was, and still is, one keypress away; what the strip added was proximity, and proximity is exactly what the transient announcement keeps. The spine's standing rule that **silence is never an outcome** is the constraint the transient is designed against rather than an exception to it: it is an announcement only, no state is ever carried by it alone, and every fact it states is simultaneously readable in the object that owns that fact — the focus card, the open payment's own line, or the Evidence record. A transient holding the only copy of something would be precisely the failure this file bans everywhere else. **That last clause is a requirement on the console, not an observation about it, and the band's removal is conditional on it being built:** every refusal and every failure the console produces *itself* — a validation refusal, a precondition or lock refusal, a call that died in the console's own hands — is written into the **Evidence/Results** action history **before** its announcement is drawn, exactly as a dispatched action is. An attempt the console refused never became a request, so nothing else in the system will ever record it; if Evidence does not, the announcement is the only copy and the removal of the band has cost the session a fact. This is the one dependency the removal has, and it is named here rather than assumed (see Component Patterns, *Transient announcement*).

**Switchable workspaces:**

| Workspace | Reached from | Purpose | Capabilities it hosts |
|---|---|---|---|
| Operations | Nav rail / `1` | Submit payments and watch them settle | Stage-focus layout, three regions on one continuous surface: a two-line **compose bar** (account pair, amount, rail, idempotency mode, Submit, Burst…), one large **focus card** rendering the selected payment and carrying that payment's own action — Cancel payment, Look up outcome, Resend same key — and a **STILL OPEN** strip listing every payment with no proven outcome yet, one compact line each, under a captioned rule whose right end states the feed status. Selection drives the card, so the selected line and the big card are one object. A running burst takes the whole content area over. Session history is deliberately not here |
| Resources | Nav rail / `2` | Control the running topology | Start/attach/stop/switch AppHost, per-resource start/stop/restart, Dev Proxy arming for the next AppHost start, replica count + scale-if-supported |
| Evidence/Results | Nav rail / `3` | Inspect what happened in depth | Full response detail (code/latency/body), inbox/outbox contents, balance/conservation, action history — **attempted actions, not only dispatched ones: every refusal the console produced itself (validation, precondition, lock) and every call that failed in its own hands is a record here before its announcement is drawn** — and the live broadcast **event feed** — every `transaction-events` CloudEvent the console has heard this session, including ones from payments this console did not submit |
| Load Test | Nav rail / `4` | Run and read the accepted mixed-rail workflow | Reset→Run→Wait→Assert→Investigate phases (Reset is Run's own first internal phase, not a standalone control), five invariants, inline-instant-settlement proof |
| Faults | Nav rail / `5` | Set how hard the system is being broken, and prove it took effect | Error-rate, latency-band, and throttling sliders; named presets loaded from the checked-in Dev Proxy profiles; staged-vs-live diff; Apply; panic-off |

No workspace is more than one keypress from any other; none contains a nested sub-navigation. A workspace that needs a topology it doesn't currently have (for example, Load Test needs the LoadTests AppHost; Faults needs a topology whose Dev Proxy was armed at start) shows why it's unavailable and a one-step remedy action, rather than hiding itself or silently degrading — this keeps the IA shallow even across the two-topology constraint.

**Why Faults is its own workspace and not part of Resources.** Resources answers *"is it running?"*; Faults answers *"how hard is it being broken?"* — a different question with a different unit of control (a continuous level, not a discrete command) and a different safety model (reversible and un-confirmed, not destructive and `Y`-gated). Three sliders plus preset chips plus a staged-versus-live diff plus Apply need a full content area and their own fixed lower action region; folding them into Resources — which already hosts the AppHost control panel and one row per resource — would force either a scroll or a sub-panel, and a sub-panel is the nested sub-navigation this IA bans. Resources keeps exactly one fault-related control: the **arming toggle**, which is a launch-time property of the topology, not a level.

**Why Operations shows no history.** Operations holds what is happening; **Evidence/Results** holds what happened. The STILL OPEN strip is a work queue, not a log: a payment enters it when it is submitted and leaves it when it is proven, and the strip renders at all only while more than one payment is open — with one open the card is already showing it, and listing it again beneath itself would be the duplication this revision exists to remove. Below that threshold the strip collapses to zero rows, captioned rule included, and that collapse is the point: it is what lets a settled focus card own the entire content area rather than share it with results the operator has already narrated. The feed status the rule carries moves with it, right-aligned at the foot of the card region, because the one statement that says whether anyone is listening must never be the thing that disappears. Duplicating the session's history in Operations was the space cost the operator objected to — permanent rows spent re-stating records that Evidence/Results already holds authoritatively, next to the live event feed, one keypress away. The record was never in Operations to begin with, so nothing is lost by not drawing it twice.

**Why the outcome feedback loop adds no surface.** It is the one capability here that is not something the operator *does* — no control to place, no level to set, no command to fire — and a truth that arrives belongs beside the thing it is the truth about. It lands in exactly two places: **in place** on the Operations focus card for a single payment — and on that payment's STILL OPEN line while it is still open — and in the **Evidence/Results** feed for a burst, whose outcomes must be counted rather than followed. Feed status rides on the region that holds the waiting payments and on the feed header, never the topology bar. The rejected alternatives — a sixth workspace, a persistent event lane, a stage banner, a feed-status chip — are listed once in **Inspiration & Anti-patterns** below, with their reasons, and not repeated here.

**Main workspace composition** (Operations, Resources, Evidence/Results, Load Test, Faults content areas): each reads as one operational activity surface, not a cockpit panel. **Resources**, **Evidence/Results** and **Load Test** render their content as a list of `DESIGN.md` **Activity rows** — a bold verb/object headline ("Stop — corebank-api", "Submit — standard payment") with the exact command/request detail muted directly beneath it, and a truthful status marker held in a fixed-width left gutter, never inline-mixed with the headline. **Faults** is a fixed set of labelled controls rather than a scrolling row list, and **Operations** is the three-region Stage-focus layout described above — a compose bar, a focus card and one-line strip rows, none of which is an Activity row. All five obey the same rules regardless: borderless, on the one continuous `surface-base` tone, and (for the three that still have one) with the primary action anchored in the same fixed lower action region. This replaces the earlier claim that Faults was the single exception to an Activity-row list; the Stage-focus Operations layout made that claim false.

**Where the primary action lives — and the one workspace that no longer obeys the rule.** In **Resources**, **Faults** and **Load Test**, each workspace's one primary action (and, in Resources, the selected row's contextual action) anchors in a fixed lower action region at the bottom of that content, so the eye's path is rows above and action fixed below, with no boxed sub-panel breaking the flow. This rule previously read "each workspace" and placed that region "directly above the persistent Evidence strip"; both halves are overridden here (brief §8) — the strip no longer exists, and **Operations is exempt**. Operations is composed instead as three stacked regions on the one continuous `surface-base` tone, separated by captioned hairline rules: the compose bar, the focus card, and the STILL OPEN strip. Its actions anchor to the object they operate on rather than to a shared region: Submit and Burst… sit on the compose bar whose contents they act on, and the payment's own action (Cancel payment, Look up outcome, Resend same key) sits on the focus card, acting on the payment printed above it. Two things force the exemption and neither is true of the other three workspaces. Removing the bottom band took the fixed lower region away. And Operations is the only workspace holding two live objects at once — a payment being composed and a different payment being watched — so a single shared action slot could no longer say which of them it meant, and an operator mid-sentence must never have to work that out. Resources, Faults and Load Test each act on one thing at a time and keep the original rule unchanged.

## Voice and Tone

Microcopy. Brand voice/posture lives in `DESIGN.md` Brand & Style. The console narrates truth the operator will read aloud on stage (brief §6 "Latency honesty," "Truthfulness on failure") — plain, factual, and status-vocabulary-exact.

| Do | Don't |
|---|---|
| `202 Pending — no committed outcome yet` | `Something went wrong, please wait...` |
| `504 Cancelled — the rail's budget expired and the payment was provably withdrawn; no money moved` | `504 Gateway Timeout` (a transport word for a proven business outcome) |
| `cancel refused (409) — the bank reports status Processing` | `The bank is executing it right now` (a claim about the bank's internals the console never observed) |
| `Ambiguous — not yet reconciled; Resend is unsafe; a fresh submission or an outcome query is the only way forward` | `Retrying...` (implying it is safe when it is not) |
| `Attached — this AppHost is not owned by this session` | `Connected` (hides the ownership distinction that gates Stop) |
| `Restart CoreBank API? This will interrupt in-flight work.` | `Are you sure?` |
| `5 invariants: 4 passed, 1 failed — Instant inline-settlement: 0 observed` | `Load test failed` |
| Exact HTTP status codes and field names, always | Paraphrased or rounded evidence |
| `Awaiting settlement — 14s (listening)` | `Pending...` (silent about whether anyone is even watching for the answer) |
| `Feed lost 12:06:02 — 3 payments have unknown outcomes` | Leaving those three sitting at `Awaiting settlement` as though the wait were still meaningful |
| `Settled — ProcessedAt 12:04:31.882, observed here +222 ms` | `Settled in 222 ms` (presents delivery time as the bank's processing time) |
| `Unattributed — tx-9004 was not submitted from this console` | Listing a stranger's transaction silently among the operator's own |
| `Listening since 12:01:04 — events before this time were not observed` | An empty feed that reads as a quiet system |
| `Contradiction — HTTP proved Completed, broadcast says Failed` | Silently picking whichever answer arrived last |
| `com.corebank.transaction.failed — ErrorReason: insufficient funds` | `Payment failed` (drops the reason the audience asked about) |

## Component Patterns

Behavioral. Visual specs live in `DESIGN.md.Components`.

| Component | Use | Behavioral rules |
|---|---|---|
| Topology bar | Persistent shell | Read-only display; commanded transitions (a resource/AppHost action the operator just triggered) flip that chip to `Running`/`~` immediately on dispatch, before the next poll; externally observed changes instead poll at most once every 1–2 seconds and must hold the new state for one full interval before the chip updates, so a flapping dependency reads as "unstable," not as flicker; clicking a status chip opens resource detail in the Resources workspace, never mutates directly; renders as a thin top context/status bar on the same `surface-base` tone as the workspace beneath it, not a boxed panel; each chip (including the persistent fault chip) is individually keyboard-focusable, not one opaque region (see Accessibility Floor) |
| Navigation rail | Persistent shell | Compact, fixed-width left column listing the five workspaces; one keypress (`1`–`5`) or click activates a workspace; active item highlighted with `accent-navy`; never hidden, never collapsed into a horizontal tab strip, never nested; shrinks to icon+shortcut only below the preferred terminal width, labels hidden but switching stays one key |
| Status chip | Topology bar, Resources, and every Activity/Resource row's status gutter | Read-only; symbol + label + color together, never color alone; four resource states (`Healthy`/`Running`/`Unknown`/`Failed`) plus the independent fault chip (`Unavailable`/`Armed`/`Faults in force`); `Unknown` (stale/unparseable Aspire snapshot) is worded distinctly from `Unreachable` (the console itself cannot reach the resource's HTTP/Aspire endpoint — a transport failure on DemoRunner's own side, not a claim about the resource); both disable that resource's mutating commands until a fresh read succeeds |
| Activity row | Every workspace's main content | Bold verb/object headline, muted command/request detail directly beneath it, and a status marker in a fixed-width left gutter; rows sit directly on the continuous work surface, borderless, so the list reads as one operational activity surface rather than stacked cards (see `DESIGN.md` Activity row); before any row exists yet, shows one muted placeholder row stating the workspace has no activity this session — never a blank void |
| Resource row | Resources workspace | An **Activity row** whose fixed action slot shows the single legal next command (Start/Stop/Restart) for that resource; the slot's position never moves when the label changes, so the recovery action for a stopped resource lands exactly where the stop action was; during a commanded transition, the row shows an elapsed-time readout ("Restarting — 4s") in its meta line rather than a bare spinner, per the same latency-honesty rule as the Load phase strip's Wait phase |
| AppHost control panel | Resources workspace | Start / Attach / Stop / Switch for Regular and LoadTests, each with the same elapsed-time-while-transitioning treatment as a Resource row. Whole-AppHost Stop **and** Switch are both disabled (visibly, not hidden) whenever the current topology is Attached — Switch is a compound stop-then-start and cannot proceed on a topology that this session doesn't own any more than a plain Stop can. On an Attached topology, allow-listed, fingerprint-verified, individually confirmed per-resource Start/Stop/Restart commands remain permitted — ownership (whole-AppHost) and resource control are tracked and gated independently, as codified by amended `ADR-015`. Switch is classified destructive and gated by the **Confirmation modal** exactly like Stop |
| Compose bar | Operations workspace | Replaces the former **Payment form** row. Two captioned lines: `From <iban>` and `To <iban>` with **Submit** anchored at the right edge of the first; `Amount`, the rail chip (`standard`/`instant`) and the idempotency chip with **Burst…** anchored at the right edge of the second. `[ASSUMPTION]` The account pair is preset and editable inline; amount and rail stay explicit fields, never file edits. Two eighteen-character IBANs and their captions consume most of the content pane's width on their own — at the 80 usable columns the 16-column navigation rail leaves (`DESIGN.md` Layout & Spacing owns that derivation) — so the amount, the two chips and the second action cannot share their line; the captions are what stay, because an unlabelled IBAN read from the back of a room is a run of digits. A third line exists only where a mode needs one — the supplied-key field in Supplied mode, the not-retry-safe warning in Omitted mode — so no control in use is ever hidden and the deduplication demo stays one keystroke deep. **Currency is not an operator input** (brief §6): there is no currency field and no currency validation rule, and the console always sends `EUR`. `[ASSUMPTION]` Every seeded demo account is denominated in EUR — pending confirmation, and the only thing that makes a fixed currency safe to send. Submit belongs to this bar, not to a workspace-level action region, which Operations no longer has (see Information Architecture) |
| Idempotency selector | Operations workspace, part of the compose bar | `[ASSUMPTION]` Three explicit modes — Generated (default), Supplied, Omitted; Omitted is visibly labeled "not retry-safe after an ambiguous outcome" before submission, not after. Because PaymentsAPI makes the transaction id *be* the idempotency key (see Foundation, **Outcome-feedback boundary**), Generated and Supplied hand the console the payment's identity before the request leaves; Omitted alone leaves the console with nothing to name the payment by until the bank answers, which is why **Cancel payment** renders disabled with that reason on an Omitted submission still in flight. That is the same cost the mode's label already names, stated concretely, and not a second limitation |
| Focus card | Operations workspace | One large object rendering the **selected** payment, and the only place in Operations a payment is read in full. Top line: the state symbol, the state word (cased and weighted per `DESIGN.md` Focus card), the elapsed clock while the payment is unresolved or the final clock once it is proven, and that payment's own action anchored at the right edge. Beneath it, the request detail (rail and amount, then both accounts printed in full — the STILL OPEN strip's last-four-digits truncation never applies here), the meta line carrying the transaction id **and that payment's own submit time as a wall clock**, and then exactly one closing block: the lifecycle in words while unresolved (`submitted ──▶ 202 Pending ──▶ waiting for the bank`), the balance legs once settled, or the `ErrorReason` once rejected. Never two blocks at once, and never a kind of block this file has not named — with **one named exception**, which is the fourth kind: a contradicted payment's closing block holds *two* records rather than one, because a contradiction **is** two records. Each is printed with its source and its time (`HTTP 200 Completed 12:04:31` / `broadcast Failed 12:04:36`), the card's state word is `✕ CONTRADICTED`, and it is never resolved to either side. That exception exists because the alternative is the silent tie-break this file bans in Interaction Primitives, made on the largest object the room can see: the card is the whole of what Operations shows, so a contradiction the card could not render would be discoverable only by switching workspaces. The elapsed clock is a duration and never doubles as a time of day; the submit stamp on the meta line is what says *when*, which matters because the card holds a resolved payment indefinitely (below). Which payment it holds is a function of selection, never of arrival — with nothing open it holds the most recently resolved payment, so a settled result stays readable instead of being cleared by its own success; with exactly one payment open it holds that one; with more than one open, the operator moves selection through the strip and the card follows. `[ASSUMPTION]` A new submission takes the selection, because the card is what the compose bar's last act produced; the revised layout stated the three standing cases and left the moment of submission implicit, and that moment is made explicit here. **A submission takes the card at the instant Submit is pressed, not when its answer arrives** — the card renders the request, a clock already running and a live **Cancel payment** (disabled in Omitted mode, per *Idempotency selector*) before any response exists, because a payment the console has sent and cannot yet describe is precisely the payment it must not leave unrepresented (see State Patterns, *Payment: no response*). The card updates in place as its payment resolves — the state word changes, the clock stops, the action slot is replaced by the next legal action — and an arriving event never re-points it at a different payment (see Interaction Primitives). An **ambiguous** payment is a card state like any other: it renders `~ AMBIGUOUS` with its closing block reading `not yet reconciled — Resend is unsafe`, and its action slot holds a disabled **Resend same key** beside an always-enabled **Look up outcome**; it must never be rendered as awaiting, because a payment whose whole point is that nothing is coming must not borrow the vocabulary of one that is waiting legitimately. Because the card holds its payment until another replaces it, a resolved payment captured under a topology, run generation or fault level other than the one now in force carries the same visible stale marking every Evidence record carries (see State Patterns, *Evidence provenance across a topology switch*), and a topology switch returns the card to its placeholder rather than leaving a settlement from a topology that no longer exists filling the largest object on the screen |
| Still-open strip | Operations workspace, beneath the focus card | Lists every payment with no proven outcome yet, one compact line each, under a captioned rule whose right end carries the feed status. It renders **only when more than one payment is open**: with exactly one, the card is already showing it and a strip beneath would list it under itself. With none open, the strip and its rule collapse to nothing at all — not an empty-state row — and the feed status moves to the foot of the card region instead; why that collapse is the point, and why no session history is drawn here, is argued once in Information Architecture, *Why Operations shows no history*. It is not a history: a payment leaves the strip the moment its outcome is proven, and only then. **`Outcome unknown` payments therefore stay in the strip and are not a special case** — unknown is not proven, and these are the payments the operator most needs listed; each stays listed until something proves it finished, and selecting one brings **Look up outcome** within a single keypress on the card above. The strip carries no per-line action: its rows are three cells of marker and status followed by the payment's own figures, and an action slot there would cost the truncated identifiers the room reads. So does a submission whose response never arrived (see State Patterns, *Payment: no response*), keyed by its idempotency key: the strip's job is every payment the console cannot account for, which is what makes its absence safe to read as *nothing is open* and never as *nothing went wrong*. Account identifiers truncate to their last four digits here and only here, because two eighteen-character IBANs plus an amount, a rail and a clock overrun even the widened content line; the card above always prints them in full. A leading gutter marks which line the card is showing, and moving selection through the strip re-points the card. Rows hold submission order — the one permitted movement is a resolved payment leaving, which does not violate the standing no-re-sort rule because the strip lists open payments by definition. Under vertical pressure it yields rows before any other Operations region, but never falls below two while more than one payment is open, and it states the surplus rather than hiding it (see Responsive & Platform) |
| Cancel payment action | Operations workspace, the focus card's action slot | Withdraws a payment that has no proven outcome yet. Offered on **any** such payment, standard rail included: CoreBank's `POST /api/transactions/cancel` is rail-agnostic, and hiding the action on a slow standard payment would read as a missing capability rather than a design choice. It acts on the payment the card is showing, so it needs no target control and no "which one?" step. It fires immediately — no confirmation modal, no `Y`; why that is consistent rather than an exception is argued in Interaction Primitives, *Cancelling a payment fires with no confirmation*, and is not repeated here. **It is offered from the instant the payment takes the card**, which — because the transaction id is the idempotency key the console already holds (see Foundation) — includes the whole of an instant payment's budget window, before any response has arrived. It is disabled, with the reason stated, only on an **Omitted**-mode submission that has not yet answered, because that is the one case with no id to name. Its outcome is never assumed: the console renders whichever of the bank's answers it actually gets, and the bank's `200 Cancelled` is what resolves the payment — the broadcast confirms it rather than granting it (see State Patterns, *Payment: Cancel accepted*, where that rule is argued once). **On dispatch the card's *action slot* — never its state — re-states itself as `Cancelling — 3s`**, with the same elapsed readout every other commanded transition carries, while the payment's own state, clock and strip line stay exactly as they were: asking is not an outcome. Duplicate activation is debounced to one dispatch, as everywhere else, so a second press mid-sentence cannot become a second cancellation. If the call fails, times out, or answers something the console does not recognise, the slot returns to **Cancel payment**, the announcement prints the exact status or the exact transport failure, the request itself is on record in Evidence — and the payment is left precisely where it was: a cancel whose reply never arrived asserts neither success nor failure, and never implies the payment was withdrawn. `[ASSUMPTION]` It is not one of the single-action-in-flight lock's named exemptions and does not wear the lock-exempt outline — the brief exempts it from confirmation, not from the lock — so it dims like any other mutating control while some other action is genuinely in flight; the payment it cancels is never that other action, because an outstanding answer is that payment's own state rather than a console action awaiting a result, which is exactly what makes the budget window cancellable. Cancel adds no endpoint to any banking service; the console calls the one CoreBank already exposes |
| Resend-same-key action | Operations workspace, the focus card's action slot, after a Generated/Supplied submission | `[ASSUMPTION]` First-class button, not a hidden re-submit; disabled entirely (not just discouraged) after an Omitted-key submission that resolved ambiguously |
| Burst control | Operations workspace, reached from **Burst…** on the compose bar | Bounded count field (enforced min/max), showing two labeled lines of running totals: **Sent** (`Sent  200 / 200   accepted 200 · failed 0` — what the API answered) and **Settled** (`Settled  187   rejected 0 · still moving 13 · unknown 0` — what the broadcast confirmed, and what nothing confirmed). These lines were called the *HTTP leg* and the *proven leg* until this pass; the leg vocabulary named the plumbing rather than the meaning and failed the read-aloud test on its own author, so it is retired here and everywhere else in this file (brief §3). The two lines are never merged, because a burst is exactly where "acknowledged" and "finished" diverge, and `still moving` draining to zero is the burst's visual confirmation. `still moving` is the awaiting count under a name the room can hear: it goes up as submissions are accepted and down as events arrive, it is never a countdown, and it is never decremented by a timeout. **A payment whose send failed has no proven outcome and is counted as one:** the **Settled** line carries a fourth figure, `unknown <n>`, holding every payment whose HTTP call failed and every payment restated as unknown by a feed loss, so `settled + rejected + still moving + unknown` always equals `accepted + failed` and the room can do that arithmetic straight off the screen. Without it, a Dev Proxy-injected `503` on the response path of a call CoreBank may well have executed simply falls out of the accounting — which is the burst-scale form of the single failure this console exists to prevent. `Sent`'s denominator is always the **requested** count and never re-bases: a stopped or partially-sent burst still reads against the number the operator asked for, because "two hundred of two hundred sent" is one word away from "two hundred of two hundred done" and the denominator must not quietly move to make a partial run look complete. A single proportional bar reinforces the printed figures and never replaces them — the numbers are the reading, the bar is the glance — and its caption names which figure it carries, because with any rejections at all the proven count and the `Settled` figure diverge: `188 of 200 settled or rejected`. Its **Cancel** control, labelled **Stop sending** in the takeover, is one of the console's named exemptions from the global single-action-in-flight lock (see State Patterns; the Faults workspace's controls are the other) — it stays enabled for the full duration of the burst it belongs to and cancels without discarding evidence already captured; apart from the fault controls, every other mutating control everywhere else stays disabled until the burst resolves or is cancelled |
| Burst takeover | Operations workspace, for as long as a burst is running or holding its result | A running burst **replaces** the compose bar, the focus card and the STILL OPEN strip and occupies the whole content area, rather than rendering as one more object among them: during a burst the counters *are* the demonstration, and they are what the back of the room has to read. Its captioned rule names the run (`BURST · 200 instant payments · 4 at once`) with the elapsed time at the right end while it runs and the drain time once it is done; its body is the two counter lines and the bar; its action slot holds **Stop sending** while sending and **Done** once drained. **The rule also carries the region's feed statement, beside the run clock at its right end** — the one thing the takeover inherits from the three surfaces it replaces, because it replaces every surface that says whether anyone is listening and `still moving` is a count of payments the console is *currently listening for*, unreadable without it. On feed loss the **Settled** line itself changes rather than the screen gaining a badge: `still moving` leaves it at that instant and the line reads `Settled 187 · rejected 0 · unknown 13 — the console stopped listening at 12:06:02`, in `state-neutral`, so the takeover is structurally incapable of displaying a wait nobody is performing, exactly as an open payment's own line is. A counter that froze at a number whose meaning had silently changed from "waiting to hear" to "nobody is listening" would be the one failure this whole capability exists to prevent, held on the most-watched screen the console has. On drain it **holds** — the final Sent/Settled summary stays on screen until the operator dismisses it, because a result that clears itself on completion is a result the room never got to read, and the drain to zero is the beat this capability exists for. **Its closing line is conditional and is printed only when it is true:** `every payment proved itself · nothing left awaiting` requires `still moving 0`, `unknown 0` and `failed 0` together; otherwise the same place states the shortfall — `12 payments have unknown outcomes — see Evidence`. A drained burst is not the same thing as a proven burst, and the longest-lived, loudest sentence this console renders must never say it is. A burst the operator **stopped** is captioned distinctly — `stopped after 6.2s · 120 of 200 sent`, never `drained in` — and the bar's denominator becomes the sent count with the unsent remainder stated as its own figure, so a permanently partial bar is never read as payments that failed to prove themselves. Individual burst payments never enter the STILL OPEN strip and never take the focus card: they are counted, never listed, which is the same boundary the Evidence feed keeps for events it cannot attribute |
| Outcome query | Operations workspace, the focus card's action slot | Looks up the card's own payment by its captured id or key — no typed target, because the card already names one. The standing captioned **Outcome key** field it used to be is retired as a label and as a control (brief §7); the capability is unchanged and so are its rules — always enabled, read-only, never blocked by the single-action-in-flight rule, visually identical whether or not another action is in flight. It is not the only road to an outcome; it is the deliberate second opinion — the move whenever the card or an open line reads `Outcome unknown` or `Outcome not observed — no feed`, or the room wants the answer pulled rather than pushed. It is never disabled because the feed is listening, and it remains the documented remedy for a feed that has been lost |
| Fault arming toggle | Resources workspace | Replaces the former on/off DevProxy toggle. Arming is a **launch-time** property, because `Features:UseDevProxy` is read when the AppHost starts: this toggle sets whether the *next* AppHost start brings up a Dev Proxy, and it is labelled in those words — never as a live on/off switch, which it cannot be. On an already-running topology it shows the topology's actual armed state read-only, with the one-step remedy (restart the AppHost armed) stated rather than implied. Disabled with the reason shown on an Attached topology, which this session did not start and therefore cannot re-arm. Its state is mirrored live as the persistent topology-bar fault chip |
| Fault slider | Faults workspace | One per knob — **error rate** (share of intercepted calls answered with an injected 503/429/500), **latency band** (a two-handle range, floor and ceiling, applied per intercepted call), **throttling** (permitted requests per rate-limit window). Arrow keys move the focused handle by one step, `Shift`+arrow by a coarse step, `Home`/`End` jump to the knob's floor/ceiling; the mouse drags the handle. Moving a slider has **no effect on the running system** — it stages a value (see State Patterns, Fault levels). Each slider always renders its exact numeric value as text beside the track, never the bar alone, so the level can be read aloud precisely and survives a monochrome terminal. Severity is **never** encoded in color (see `DESIGN.md` Do's and Don'ts) |
| Fault preset chips | Faults workspace | Named starting points loaded from the checked-in Dev Proxy profiles — the Regular profile's shipped levels, the LoadTests profile's instant-rail-overrun latency band, and `All off`. Selecting a preset **stages** every knob at once; it never applies directly, so a preset and a hand-dragged value go through the identical Apply path. The preset list is per-profile: the LoadTests instant-rail-overrun band is offered on the LoadTests topology, where it is the tuned default, and the currently selected preset name is shown until any knob is moved away from it, at which point the label reads `Custom` |
| Apply faults action | Faults workspace | The workspace's single primary action. Commits **every** staged knob in one config write, so the running system never observes a half-applied combination. Not destructive and not `Y`-gated: it injects no data loss, is fully reversible, and is undone by a single key. Disabled — visibly, with the reason — when nothing is staged, so a repeated press cannot silently rewrite an identical config |
| Panic-off control | Faults workspace, and `0` from every workspace | `0` is chosen because it sits beside the `1`–`5` workspace keys the operator's hand already lives on, and because "zero" is what it does. Sets every knob to zero and applies immediately, in one step, with no confirmation and no staging. Always enabled, exempt from every lock, and never hidden — de-escalation must never be gated behind the thing that is currently going wrong. Deliberately asymmetric with Apply: making the system worse takes a deliberate two-step (stage, then Apply), making it better takes one key |
| Fault chip | Topology bar, persistent | Three states, text+symbol, never color alone: `Unavailable` (this topology started unarmed, or is Attached), `Armed` (a Dev Proxy is running but every knob is zero — nothing is being injected), `Faults in force` (at least one knob is non-zero and applied). It shows *that* faults are live, never *how severe* — severity is a number the Faults workspace owns. Clicking it activates the Faults workspace, exactly as a resource chip opens Resources |
| Replica indicator | Resources workspace | Always shows the current count; the scale control itself is present only when the supported Aspire command surface actually allows scaling for that resource — otherwise it's a read-only figure, never a disabled-looking button that implies it should work |
| Load phase strip | Load Test workspace | Renders `Reset → Run → Wait → Assert → Investigate` exactly as the accepted workflow defines it; Reset is Run's own first internal phase — there is no standalone, generic Reset control anywhere in the console, and every rerun (including Journey B's repeated reruns across planted-bug branches) resets the disposable topology again through this same accepted sequence, never a shortcut around it; no second, DemoRunner-invented assertion path. Before any run this session, all five phases show `not-yet-reached` |
| Invariant chip | Load Test workspace | One chip per invariant (exactly-once, no-loss, balance-conserved, ordering, drained) plus a distinct inline-instant-settlement chip; each shows pass/fail/not-yet-observed individually — never collapsed into one pass/fail bit; before any run this session, all chips show `not-yet-observed` |
| Feed status (inline) | Awaiting payment rows; Evidence feed header; the Operations STILL OPEN rule, or the foot of its card region when nothing is open; the burst takeover's captioned rule while a burst holds the workspace | The console's ability to hear the broadcast is stated **on the rows that depend on it**, never as its own chip or indicator — an awaiting row reads `Awaiting settlement — 14s (listening)`, and the Evidence feed's header reads `Listening since 12:01:04 — events before this time were not observed`. The transition that matters is loss: the moment a subscription drops, every payment still awaiting an outcome changes state to `Outcome unknown — the console stopped listening at <time>` (see State Patterns), because a payment nobody is listening for is not pending; it is unobserved. This is the whole honesty mechanism and it needs no chrome: the console cannot display a stale `Awaiting settlement` while it is not listening, because those words are removed from the screen at the instant they stop being true. On reconnect the feed header stamps the gap explicitly (`Listening again — no events observed 12:06:02–12:06:19`) and never back-fills it; rows already marked `Outcome unknown` stay that way until an **Outcome query** resolves them, because a resumed subscription is not retroactive evidence. In the Stage-focus Operations layout the statement is made **once for the region** instead of being repeated on every open line: the STILL OPEN rule's right end reads `listening since 14:02:11`, when the strip is collapsed that same statement sits right-aligned at the foot of the card region, and during a burst it rides the takeover's own rule (see *Burst takeover*). **The statement has a negative form and is never absent:** when nothing is listening it reads `○ not listening since 12:06:02 — outcomes will not arrive here`. Only its words change — it is never blanked, never reduced to a symbol and never surrendered at any width, because dropping the line is the obvious implementation and a blank where the console's most important sentence used to be reads as nothing being wrong. This overrides the per-row `(listening)` qualifier in Operations only — Evidence/Results keeps its header and its inline form — and it costs nothing, because the parenthesis was never the honesty mechanism: the state change is. The instant the feed drops, the card and every open line re-state themselves as `Outcome unknown`, exactly as before |
| Event row | Evidence/Results event feed; condensed on the focus card in Operations, as that payment's closing block | An **Activity row** for something the system said rather than something the operator did, distinguished by an inbound gutter marker (`<`) and past-tense grammar (`Settled — tx-8821`) rather than by color (see `DESIGN.md` Event row). The meta line always prints the CloudEvent type verbatim, the transaction id, and — as **two separate figures** — the event's own `ProcessedAt` and the console's observed-at time; the console never presents delivery latency as the bank's processing time. A `com.corebank.transaction.failed` row always carries its `ErrorReason` in full; a truncated reason is the one thing an audience will ask about |
| Settlement legs | Beneath a settled payment on the Operations focus card, and beneath its row in Evidence/Results | The two `com.corebank.account.balance.updated` events for one payment render as two aligned lines in a fixed column — `1001  −250.00 → 4,750.00 EUR` and `2002  +250.00 → 1,180.00 EUR` — the most literal proof available that money moved, and the one the room reads fastest. Per Foundation's event contract, two legs per settlement and none for a rejection — so the console must never label a payment "both legs settled" on the strength of one. While only one has arrived it reads `1 of 2 legs observed`, and if the second never comes it stays there: a visibly half-settled payment is a real finding worth showing, not a rendering gap to paper over. An empty leg column under a `Rejected` row is the expected rendering rather than a missing one — the row's status label is what tells the two apart. Balance events are also rendered on their own in the Evidence feed even when no payment row claims them |
| Primary action button | The fixed lower action region of Resources, Faults and Load Test — Operations has none (see Information Architecture), because its actions anchor to the compose bar and the focus card instead | Exactly one per workspace that has one, Enter/click fires it; when that workspace's primary action is itself destructive (Load Test's **Run**, because Reset truncates the disposable topology's stores as its first phase), it renders and behaves as a **Destructive action button** instead, gated by the **Confirmation modal** every time Run fires, including Journey B's repeated reruns |
| Destructive action button | Resource Stop/Restart, AppHost Stop/Switch, Load Test Run | Fires only after the **Confirmation modal** is answered with its typed key; its resolved/inverse action always renders in the exact screen slot the original occupied (Stop → Restart in the same resource-row slot) |
| Transient announcement | Foot of the content area, every workspace | Replaces the removed **Evidence strip**; the argument for that removal has one home, in Information Architecture, *Override — the bottom band is removed from every workspace*. A failed or refused command states itself in one truthful line, in the same exact-status, exact-reason vocabulary the strip used (`✕ The source and destination account must differ.`), and then clears. **It takes the tone of the thing it announces and never a fixed one:** a command that ran and was refused is a proven failure and renders as one; a notice that is no verdict at all — a lost feed, a reconnection, a palette switch — renders in the neutral tone the rows behind it are taking at that instant. A lost feed proves nothing about any payment, and an announcement must never assert a failure the states beneath it are carefully declining to assert (`DESIGN.md` fixes the tokens; the constraint this file imposes is that the two forms exist and that the second is not the failure token). It announces failures and refusals **only**: an arriving broadcast outcome never claims it, because an outcome belongs to the card and the line it is the outcome of, and the strip's old habit of announcing settlements the operator did not trigger is deliberately not carried over. It never displaces something the operator is reading a confirmation from — while a confirmation modal is open the announcement waits behind it and appears the moment the modal closes. It never carries a fact that is not already durable: the same line is an Evidence/Results record from the moment it appears — **written there first, refusals the console produced itself included**, which is the requirement the band's removal is conditional on (see Information Architecture) — and that record, not the announcement, carries the topology/profile and run generation it was captured under (see State Patterns, Evidence provenance). The refusal also outlives its announcement in the object that owns it: the compose-bar field the refusal names carries an inline marker until the operator changes it, so a cleared announcement can never leave the screen looking byte-identical to a successful submission, with the previous payment's settled card filling it. A stale focus card is never the answer to the last keypress, which is why the card's meta line stamps its own payment's submit time (see *Focus card*). It takes no focus, reserves no row when there is nothing to say, and shows no placeholder before the first action this session — an empty foot is the resting state. `[ASSUMPTION]` It clears after a few seconds or on the next action, whichever comes first; the exact dwell is an implementation choice, and the only requirements this spine makes are that it outlasts being read aloud and that nothing is lost when it goes |
| Confirmation modal | Any destructive Resources/Load-Test-Run action (resource Stop/Restart, AppHost Stop/Switch, Load Test Run) | Names the exact target and exact command; opens with focus on **Cancel** (the safer default) and traps focus entirely while open — nothing else on screen is reachable; the single explicit confirmation key is `Y`; `Escape` cancels; on either outcome, focus returns to the exact control that opened it. No hold-to-confirm gesture and no double-Enter confirmation exist anywhere in this console |

## State Patterns

| State | Surface | Treatment |
|---|---|---|
| Owned vs Attached AppHost | Topology bar, Resources workspace | Explicit badge, never inferred; Attached disables the whole-AppHost Stop **and** Switch controls (visibly, not hidden) but still permits allow-listed, fingerprint-verified, per-action-confirmed resource-level commands — ownership and resource control are tracked and gated independently, as codified by amended `ADR-015` |
| Resource: Unknown | Topology bar / Resources | Stale or unparseable Aspire snapshot; shown as `state-neutral`/`○` labeled `Unknown`, all mutating commands on that resource disabled until a fresh read succeeds |
| Resource: Unreachable (transport failure) | Topology bar / Resources | The console's own HTTP/Aspire-CLI call to check this resource failed — distinct from `Unknown`'s stale-snapshot meaning and distinct from Aspire itself reporting the resource stopped; shown as `state-neutral`/`○` labeled `Unreachable`, with the meta line naming the specific failed call; all mutating commands on that resource disabled until a fresh read succeeds |
| Resource: Healthy / Running / Failed | Topology bar / Resources | `state-healthy`/`●`, `state-running`/`~`, `state-failed`/`✕` respectively, always text+symbol, never color-only |
| Resource/AppHost transitioning (Start/Stop/Restart/Attach/Switch) | Resources workspace, AppHost control panel | Extends latency honesty beyond Load Test: show `state-running`/`~` immediately and re-enable mutations only after Aspire confirms resolution. See Component Patterns, Resource row and AppHost control panel |
| Payment: Pending | Operations / Evidence | `202`, amber, labeled `Pending` — genuinely unresolved, background delivery continues. Every standard payment answers this way, and an instant payment answers it only when its budget was exhausted *and* the cancellation outcome was genuinely unknown; a budget-exhausted instant payment whose withdrawal was proven answers `504 Cancelled` instead and is not this state (see the row below) |
| Payment: Cancelled by the rail (`504 Cancelled`) | Operations focus card, Evidence | The instant rail exhausted its budget and CoreBank confirmed the command was withdrawn before it executed, so the **submission itself** answers `504` with `Status: Cancelled`. The card resolves immediately to `⊘ CANCELLED BY THE RAIL`, which is the one place the console distinguishes *who* withdrew a payment rather than only *that* it was withdrawn. The outcome for the money is identical to an operator-fired cancellation, and the symbol and colour are identical for that reason; the state word differs because the room should not need the presenter to explain which of the two just happened. It is the seventh and last card state word, and it fits `{spacing.focus-card-state-column}` with room to spare. The payment leaves the STILL OPEN strip the instant that answer lands, exactly as any proven outcome does. It never sits there awaiting an event: the submission's own answer already proved it, and a `com.corebank.transaction.cancelled` broadcast, if one follows, is confirmation. `504` is a **proven** outcome here and is never dressed as a transport failure; a `504` whose body does not say `Cancelled` is an ordinary gateway failure and renders as one. This row exists because the rail gained the behaviour after this spine's first Operations pass, which described `202 Pending` as the only budget-exhaustion answer; that description is overridden here and in Foundation, and the Key Flow beats written against it are corrected in Key Flows |
| Payment: no response | Operations focus card and STILL OPEN strip, Evidence | A submission whose response never arrived — transport failure, timeout, or a fault-injected error on the response path — **is not an un-submitted payment and is never treated as one.** The card already holds it (it took the card when Submit was pressed) and it enters the STILL OPEN strip immediately, keyed by its idempotency key, reading `○ Outcome unknown — no response; this payment may or may not exist`, with the clock still running. It never reads `Failed`: nothing failed that the console can prove, and the money may well have moved. It stays there until an **Outcome query** on that key resolves it. In Omitted mode there is no key to hold, and the console says so in the same line rather than dropping the payment — `no response and no key — this payment cannot be looked up` — which is the concrete cost the Omitted-mode warning names before submission. This is what makes the strip's collapse safe to read: its absence means *no payment is open*, never *nothing went wrong* |
| Payment: Ambiguous | Operations / Evidence | An Omitted-key request whose outcome could not be reconciled; amber, labeled `Ambiguous — not yet reconciled`, Resend disabled; only a fresh submission or an outcome query can move it forward, without implying the outcome is permanently unresolvable. On the focus card it renders `~ AMBIGUOUS` with its own closing block and a disabled Resend (see Component Patterns, *Focus card*), never borrowing the awaiting rendering |
| Payment: Completed / Failed | Operations / Evidence | `200`, green (`Completed`, business success) or the failure reason rendered plainly (`Failed`, business rejection) — both are *proven* outcomes and both are distinct from `Pending` |
| Payment: Awaiting settlement | Operations, Evidence | Submitted, acknowledged, no broadcast outcome yet. Amber, elapsed-time readout, and the feed's own state named alongside it (`Awaiting settlement — 14s (listening)`) so the wait is never ambiguous about *who* is waiting — in Operations that statement is made once for the region rather than on each open line (see Component Patterns, Feed status (inline)), and the state itself is unchanged by where the sentence is printed. **Silence is never an outcome:** no elapsed time, however long, converts this to `Failed`. Only a `com.corebank.transaction.failed` event, or an outcome query the operator ran, can prove a rejection — this is the standing ban on treating elapsed time as a proxy for success, applied to its inverse |
| Payment: Settled (observed) | Operations, Evidence | A `com.corebank.transaction.completed` arrived and matched this row. Green, labeled `Settled`, with `ProcessedAt` and the observed-at delta as two separate figures, plus the balance legs as they arrive. The card updates **in place**, in the position it already occupied — it never re-sorts, never jumps, and never steals focus, because the operator may be mid-sentence with a finger on it. The payment does leave the STILL OPEN strip at the moment it resolves, since the strip lists open payments by definition; that is the one list movement this console permits, and it is safe because the strip is not where the outcome is read. `[ASSUMPTION]` If the payment that resolves is the selected one, the card keeps it — the resolution is read on the card that was already showing it, and selection moves on only when the operator moves it or submits again; the revised layout states which payment the card holds in each standing case and is silent about the instant of transition, and the governing rule for that instant is the existing one: a pushed outcome never re-points the screen |
| Payment: Rejected (observed) | Operations, Evidence | A `com.corebank.transaction.failed` arrived and matched this row. Rendered with the same weight as a settlement — red, labeled `Rejected`, with `ErrorReason` in full. A business rejection is a *proven* outcome and this console treats it as one — the feedback loop only makes it arrive on its own |
| Payment: Cancel accepted (`200 Cancelled`) | Operations focus card | The operator fired **Cancel payment** and the bank withdrew the payment before it executed. **The `200 Cancelled` is itself the proof and resolves the card on arrival** — it is CoreBank's own committed statement about its own row, the same class of evidence as the instant rail's `200 Completed`, not an inference drawn from a status code. `com.corebank.transaction.cancelled`, when it comes, *confirms* it and supplies `ProcessedAt` and `Reason`; when it does not come — CoreBank publishes nothing for a replayed cancellation — the payment is proven anyway and the card says so rather than hanging at awaiting while the console holds the answer in its hand. This resolves a rule this file previously stated two ways: the broadcast is what resolves a cancellation *this console did not request*, and the response is what resolves the one it did. A broadcast that contradicts the response is a **Contradiction**, handled as every other contradiction is, and never a silent correction. The card resolves to `⊘ CANCELLED` with its final clock, and its closing block is two lines: "withdrawn before execution · no money moved" and "safe to retry with a new key." The second line earns its row — the operator's next sentence on stage is always whether they may send it again, and the answer is a property of the outcome, not of the operator's memory. No balance legs, ever; their absence is the expected rendering, exactly as under a rejection, and the state word is what tells the two apart |
| Payment: Cancel refused — already executed | Operations focus card | Cancel arrived after the bank had committed the payment, so it answers `200` with the committed response instead. The card resolves to `● SETTLED` — or `✕ REJECTED`, if that is what was committed — and carries "too late to cancel — the bank had already executed it" above the balance legs, so the room is told why the card now says the opposite of what the operator just asked for. The console never re-labels a committed payment as cancelled on the strength of having asked: the bank's answer wins, and it is printed with the legs that prove it |
| Payment: Cancel refused (`409`) | Operations focus card | The bank refuses to withdraw the row *now*, and its body carries that row's current status. **The console prints that status and never a sentence about what the bank is doing** — `cancel refused (409) — the bank reports status Processing`, or `status Failed` — because the one `409` outcome covers a row processing under a live claim, a row that has terminally failed, and a row that lost the claim race, and "the bank is executing it right now" is an inference the console cannot draw from a refusal. This overrides the earlier wording of this row, which asserted live execution for an answer that also means terminally failed, and would have told the room, unretractably, that the bank was working on a payment it had already given up on. The card stays awaiting **only while the returned status is non-terminal**; a terminal status in a `409` body is an outcome the console has been *told*, and it is rendered as one exactly as if it had arrived by broadcast, with the payment leaving the STILL OPEN strip. The standing rule is intact rather than bent: only a proven outcome moves a payment off `Awaiting settlement`, and a status the bank stated about its own row is proof — a refusal to act is not. The action slot keeps **Cancel payment** in the non-terminal case, because the refusal was about this instant and not about the payment |
| Payment: Cancelled | Operations STILL OPEN strip and focus card, Evidence | The resolved state itself, wherever the payment is shown. It leaves the STILL OPEN strip the moment the withdrawal is proven — on the bank's own `200 Cancelled` or `504 Cancelled` answer where the console holds one, and on `com.corebank.transaction.cancelled` for a cancellation this console did not request — exactly as a settlement or a rejection does: it is a **proven** outcome, ranked with `Settled` and `Rejected` and never with `Pending`, because the bank answered. It carries its own symbol (`⊘`) and its own word, and it is never rendered as a failure: nothing failed, and `DESIGN.md` is where the token is fixed, but the constraint this file imposes on that choice is that it must not be the failure token. A cancellation is also the one outcome that states its own next step, because it is the only one that has a safe one |
| Payment: Outcome unknown | Operations, Evidence | The feed dropped, or was never established, while this payment was outstanding. `state-neutral`/`○`, distinct from both `Awaiting settlement` (still legitimately waiting, feed alive) and `Failed` (proven). Its one-step remedy is the **Outcome query**, offered on the card, which any open line reaches by selection. This state is never entered by a timeout — only by the feed's own status changing. A payment the operator cancelled is no different and gets no shortcut: if the feed drops before `com.corebank.transaction.cancelled` arrives, the card reads `Outcome unknown` and not `Cancelled`, and it is not rendered red — asking for a cancellation is not evidence of one, precisely as submitting a payment is not evidence of a settlement |
| Single action in flight | Global, all workspaces | Starting any mutating action anywhere disables every other mutating control console-wide until it resolves. Exactly three categories stay available throughout: (1) read-only inspection — outcome query, evidence detail, topology bar reads; (2) the in-flight action's **own** Cancel control where one exists (currently only the Burst control's Cancel) — it is exempt from the lock it itself holds, so a running burst can always be stopped; (3) **every control in the Faults workspace**, plus the global panic-off key. Category 3 is a deliberate, named exception and the reason the capability exists: raising latency or error rate *while* a burst or a load run is in flight is the demonstration itself, and a lock that forbade it would forbid the only moment that matters. It is safe to exempt because a fault change mutates proxy configuration, never banking state — it cannot corrupt an in-flight payment, only degrade the conditions that payment meets |
| Destructive confirmation pending | Resources / Load Test | Modal open with focus on **Cancel**, nothing else interactive; the explicit confirmation key is `Y`, `Escape` cancels; either outcome returns focus to the exact control that opened the modal, with no side effect on cancel |
| Load workflow: Reset/Run/Wait/Assert/Investigate | Load Test | Reset is Run's own first internal phase, never a separate control; every rerun repeats the full sequence from Reset, so stale data from a prior run can never be mistaken for a genuine planted-bug regression. Each phase is a first-class state, not a spinner; a stalled Wait phase after its expected drain window looks distinctly "still waiting, not hung" via an elapsed-time readout, never a bare spinner (brief §6 "Latency honesty") |
| Workspace unavailable for current topology | Load Test (needs the LoadTests AppHost), Faults (needs a topology armed at start) | Visibly disabled with the reason and a one-step remedy action, never hidden. Both cases use the identical treatment, so "this workspace cannot act right now" is one learnable pattern rather than two |
| Workspace: cold / before first action this session | Operations, Evidence/Results, Load Test, Faults | Operations: the compose bar is fully usable immediately, the focus card reads "No payment yet this session." with "Fill the lines above and press Enter." beneath it, the STILL OPEN strip is absent entirely (nothing is open, so there is no rule and no rows), the region's feed statement sits at the foot of the card region, and burst totals read 0/0/0 until a burst is fired; Evidence/Results: one muted "No actions yet this session" row, no stale prior-session data ever appears (see Foundation, Recovery on relaunch); Load Test: all five phase-strip cells and all invariant/inline-instant-settlement chips show `not-yet-reached`/`not-yet-observed`, Run is enabled; Faults: sliders sit at the levels actually in force on the running topology — read from the session config the console itself wrote, or from the checked-in profile the AppHost started with, never at an invented zero — with the matching preset name shown and Apply disabled because nothing is staged |
| Evidence provenance across a topology switch | Evidence/Results | Every evidence record carries the topology/profile (Regular/LoadTests), the **fault levels in force at capture time**, and a run-generation label it was captured under; the fault levels are part of provenance for the same reason the topology is — a `202 Pending` captured under 12 seconds of injected latency and one captured under none are different facts, and a presenter comparing two records must never have to remember which was which; switching topologies never deletes prior evidence, but every record from before the switch is visibly, unmistakably marked with its old topology/generation — a presenter glancing back can never mistake stale Regular-topology evidence for current LoadTests evidence or vice versa. Switch itself is a compound destructive action (stop-then-start) and is gated by the same Confirmation modal as a plain Stop |
| Faults: Unavailable | Topology bar, Faults workspace | The current topology started without Dev Proxy armed, or is Attached. The Faults workspace is visibly disabled — never hidden — naming the reason and the one-step remedy (restart this AppHost with faults armed), exactly as the Load Test workspace behaves on the wrong topology. Every slider renders at `text-muted` with its value still legible, so the operator can see what *would* be applied |
| Faults: Armed, none in force | Topology bar, Faults workspace | A Dev Proxy is running and every applied knob is zero. The chip reads `Armed`, not `Faults in force` — an armed proxy that is injecting nothing must never look like an active fault, or the operator will narrate chaos that isn't happening |
| Fault levels: staged vs applied | Faults workspace | Moving a slider or picking a preset stages a value and changes nothing in the running system. A staged knob renders its live value **and** its staged value together with the delta explicit (`error rate 5% → 40%`), never the staged number alone — a presenter glancing at the screen must never read an intended level as a current one. Apply commits every staged knob at once; Reset-to-live discards staging |
| Fault levels: applied but not yet observed | Faults workspace, fault chip | Dev Proxy reloads its configuration from the file it watches, which the console writes but does not control the timing of. Between the write and the first intercepted call that actually carries the new levels, the state is `Applied — not yet observed in traffic`, with an elapsed-time readout, reusing the invariant chips' existing `not-yet-observed` vocabulary. The console never claims a level is live on the strength of having written a file |
| Fault levels: observed live | Faults workspace, fault chip | The console has seen at least one intercepted call carry the applied levels. Only now does the chip read `Faults in force` and the level render as live. This is the same discipline the rest of the spine applies to payments and invariants: a written intention is not a proven outcome, and only proof gets the confident label |
| Feed established | Awaiting payment rows, Evidence feed header | A subscription is live. `Awaiting settlement` genuinely means "the answer has not come yet," and the console has earned the right to say so — each awaiting row carries `(listening)` inline to prove it — in Operations that proof is the region's own statement instead (see Component Patterns, Feed status (inline)). The feed header states when listening began, because an empty feed is only meaningful with a start time attached |
| Feed never established | Operations, Evidence/Results | No subscription — never opened, or unavailable on this topology. No payment row ever shows `Awaiting settlement`, because nothing is awaiting anything; rows read `Outcome not observed — no feed` from the moment they are submitted, and the Evidence feed states the reason plus the one-step remedy, matching how Load Test and Faults behave when their preconditions are missing. The **Outcome query** is named in that remedy as the working alternative, so a missing feed costs the console convenience and never truthfulness |
| Feed lost | Operations, Evidence/Results, transient announcement | A live subscription dropped — the console's most dangerous condition: unhandled, it would leave every payment sitting at `Awaiting settlement` while the system quietly settled all of them, and the operator would narrate a failure that never happened. The response is structural rather than decorative: on entry, every unresolved payment **changes state** to `Outcome unknown — the console stopped listening at <time>`, so the words `Awaiting settlement` leave the screen at the instant they stop being true, and the console is incapable of displaying a wait nobody is performing. **The state persists until the subscription is re-established, and it is not only for the payments outstanding at the moment of the drop:** every payment submitted while the feed is down enters at `Outcome not observed — no feed`, exactly as under *Feed never established*, and the region's statement keeps saying so — otherwise a payment submitted into the gap would fall between these two rows and be given the one label that must be structurally impossible while nothing is listening. A running burst restates its own counters in the same instant (see Component Patterns, *Burst takeover*). A transient announcement states the drop once (`Feed lost 12:06:02 — 3 payments have unknown outcomes`), in the neutral form rather than the failure form, because a lost feed proves nothing about any payment; Evidence/Results keeps that record; nothing depends on the announcement being seen, because the payments themselves already carry the state and the region's feed statement has already stopped saying `listening`. On reconnect the missed window is stamped in the feed header and never back-filled |
| Contradicted outcome | Operations, Evidence | The broadcast disagrees with what HTTP already proved for the same `TransactionId` — most sharply, an instant-rail `200 Completed` followed by a `com.corebank.transaction.failed`. The console **never silently picks a winner and never lets the later message overwrite the earlier one.** Both records stay on screen, both stay labeled with their source and their time, and the row reads `Contradiction — HTTP proved Completed, broadcast says Failed`. **On the focus card this is the one payment state whose closing block holds two records instead of one**, and its state word is `✕ CONTRADICTED` (see Component Patterns, *Focus card*) — without that exception the card, which is the whole of what Operations shows, could render only one of the two facts and would be picking a winner by omission on the largest object in the room. This is the most valuable thing the feedback loop can surface: it is a genuine finding about the system, and a console that resolved it quietly would be hiding exactly the bug the audience came to see |
| Unattributed event | Evidence feed only | An event whose `TransactionId` matches no payment this session — from a load run, from k6, from another operator, or a late outcome for a transaction submitted before this console started listening. It is recorded in the feed, never dropped, and labeled `Unattributed — not submitted from this console`; it never appears in Operations, never touches a payment row, and never counts toward the burst's **Settled** line. Dropping these would make the feed a lie by omission; attributing them would make it a lie outright |
| Events arriving during a lock or a modal | Global | The single-action-in-flight lock and the confirmation modal freeze **controls, never the truth.** Payment rows keep resolving, the feed keeps appending, and counters keep moving behind an open modal and throughout a locked action — an outcome is not a control and cannot be gated. The modal keeps its focus trap and the arriving event never moves focus, opens anything, or alters what the confirmation key will do |
| Settlement under faults | Operations, Evidence, Faults | Injected latency and errors can delay or drop the broadcast itself, so a payment may stay `Awaiting settlement` for as long as the faults are in force — which is the demonstration, not a defect. The row's elapsed readout names the condition (`Awaiting settlement — 22s (faults in force)`), and every settlement record carries the fault levels at capture time under the existing evidence-provenance rule. The console never converts fault-induced silence into a failure |
| Fault levels changed mid-run | Load Test workspace, Evidence/Results | If any fault level is applied while a load run is between its Run and Assert phases, that run's invariant chips and phase strip are visibly annotated with the change and the time it landed. The run is not blocked and its results are not discarded — but a run whose conditions changed underneath it can never present as a clean run, because its assertions were written against fixed conditions |

## Interaction Primitives

- **Single keypress per workspace switch** (`1`–`5` or equivalent), mouse click on the navigation rail as the discoverable fallback. `[ASSUMPTION]` keyboard and mouse are full peers everywhere, not keyboard-first-with-mouse-afterthought or the reverse — both are optimized, because the brief leaves this open and the fast path assumes parity rather than blocking on it.
- **One primary action per screen** in Resources, Faults and Load Test, always in the same position, anchored in that workspace's fixed lower action region (`DESIGN.md` primary-action-button). Enter/click both fire it. Operations is the one exemption, and why it is one is argued in Information Architecture rather than repeated here.
- **Single action in flight, globally, with exactly two named exceptions.** Duplicate activation (double-click, repeated Enter) is debounced to exactly one dispatch; every other mutating control shows disabled/busy, not merely unresponsive — except (1) the in-flight action's own Cancel control (currently only Burst control's Cancel), and (2) the Faults workspace's controls and the global panic-off key, both of which stay live throughout (see State Patterns, Single action in flight).
- **Every lock-exempt control shares one visual signature** — a single `accent-teal` outline with no fill (`DESIGN.md` burst-control Cancel; every Faults-workspace control; panic-off — the same membership State Patterns, *Single action in flight* enumerates, stated once there). When the console dims for an in-flight action, the controls that remain usable are recognizable as a family at a glance, rather than each being an unexplained local exception.
- **Escalation is two-step, de-escalation is one key.** Raising any fault level requires staging it and then firing Apply; returning every level to zero is a single always-available keypress with no confirmation. This asymmetry is deliberate: a stray keypress on stage must never make the system worse, and must never be the thing standing between the operator and making it better.
- **A written config is not a live fault.** The console reports `Applied — not yet observed in traffic` until it has seen an intercepted call carry the new levels, and only then reports the level as live (see State Patterns). Dev Proxy owns its own reload timing; the console never narrates a file write as though it were an observed effect.
- **No automatic retry after an ambiguous Omitted-key mutation.** The console never re-sends on the operator's behalf; Resend-same-key is offered only when the original key is known safe to reuse (Generated/Supplied).
- **Resend-same-key is first-class**, not a hidden re-submit — it is a named, always-visible action once a Generated/Supplied submission exists that can be resent.
- **Cancelling a payment fires with no confirmation, and that is not an inconsistency.** The `Y` modal is reserved for actions that destroy state. A cancellation destroys none: no money moved, the payment is safe to resubmit under a new key, and the bank's own answer is what the console will render either way. Gating it would put this console's most dangerous gesture and one of its safest recoveries behind the same door, which is the argument that already exempts Apply and panic-off. The exemption is from the *confirmation*, never from the truth-telling: the console still refuses to show a cancellation it has not been told happened, and a cancel that was refused — or whose reply never arrived at all — leaves the payment exactly where it was.
- **Destructive actions require the single explicit typed confirmation key `Y`** in the Confirmation modal — no hold-to-confirm gesture and no double-Enter confirmation exist anywhere in this console (a held key's OS/terminal-dependent auto-repeat is not a reliable or testable substitute for a real confirmation, and Terminal.Gui has no "key held for N ms" primitive to build one from); a stray keypress on stage must never fire a stop/restart/switch/load-run by itself. Applies to: resource Stop/Restart, AppHost Stop/Switch, and Load Test Run.
- `[ASSUMPTION]` **The inverse recovery action always occupies the same screen position as the action that necessitated it** (Stop → Restart in the same resource-row slot) — recoverability is a location guarantee, not just a feature's existence.
- **Raw evidence is available on demand**, never forced onto the default view: a transient announcement is a truthful one-liner; "Details" in Evidence/Results expands the same record's full body/log without paraphrasing it. The expanded view is pannable and optionally wrap-toggled (see Responsive & Platform).
- **Reset is Run's own first internal phase for the disposable LoadTests topology** (`Reset → Run → Wait → Assert → Investigate`), never a standalone control; every rerun of the accepted workflow resets the disposable topology again through this same sequence. The Regular topology has no generic "reset to a known state" action of any kind — matching the brief's open question, resolved toward "no blanket reset on the main topology."
- **The loop takes no lock-exempt signature.** It is exempt from the single-action-in-flight lock by nature rather than by exception — a read-only listener is not a control, so it was never locked — and it therefore does **not** wear the `accent-teal` outline, which belongs to controls the operator may still press. There is nothing here to press.
- **A pushed outcome never steals attention.** An arriving event updates a row *in place*, in the position it already occupies. It never re-sorts the list, never scrolls the view, never moves focus, and never pops anything over the operator's work — the operator may be mid-sentence with the cursor on that exact row, and a screen that reorganises itself under a live demonstration is a stage failure regardless of how good the news is.
- **Selection drives the focus card, and nothing else does.** The card renders the selected payment, so the line the operator moved to and the object the card's action will act on cannot drift apart — which is why Cancel payment and Look up outcome need no target control and no "which one?" step. Arrow keys move selection through the STILL OPEN strip and the card re-renders where it stands. Selection is moved by the operator and by nothing else; the preceding rule governs what an arriving event may not do to it.
- **The palette is switchable mid-demo, and switching is never destructive.** `T` swaps between the dark and light surfaces from any workspace, like panic-off and for the same reason: a projector that washes the dark canvas out is discovered during the talk, not before it. The swap is a repaint and nothing else — it never moves focus or the caret, never scrolls or re-sorts a list, never changes the active workspace, never touches a staged or applied fault level, and never interrupts or cancels an action in flight. It is therefore exempt from the single-action-in-flight lock by nature rather than by exception, and like the outcome feed it takes **no** lock-exempt `accent-teal` signature: it is not a control on the surface at all. Like `1`-`5` and `0`, it reaches the console only when focus is not inside a text field, so typing a `t` into an account or key field is unaffected. The console states the palette it switched to on the message line, because an operator who hit the key by accident needs to know what just happened.
- **Two clocks, never one.** The event's own `ProcessedAt` and the console's observed-at time are always printed as separate figures with the delta explicit. Delivery latency belongs to the transport — and, when faults are in force, partly to Dev Proxy. Presenting it as the bank's processing time would be the same class of lie as claiming a written fault config is a live fault.
- **A contradiction is shown, never resolved.** When HTTP and the broadcast disagree about the same `TransactionId`, both records stay on screen with their sources and times, and the row says so. The console has no tie-break rule and should never acquire one; picking a winner would hide the most interesting thing it is capable of finding.
- **Banned:** a linear/next-only cue queue, slide anchors or speaker notes as a navigation dependency, auto-advance past unproven evidence, auto-retry of an ambiguous keyless payment, any generic/arbitrary command execution, direct store/broker access, treating elapsed time alone as a proxy for success, hold-to-confirm/double-Enter as a confirmation mechanism, any local journal/checkpoint claim that a prior session's state was restored on relaunch, **any write by this console to a checked-in Dev Proxy configuration file**, **any automatic or timed escalation of fault levels the operator did not fire**, **any claim that a fault level is live before it has been observed in traffic**, **any synthesised, inferred, or optimistic payment outcome the console did not actually receive**, **any timeout that converts an awaited settlement into a failure**, **any replay or back-fill of broadcast events from before this console started listening**, **any silent resolution of a contradiction between an HTTP outcome and a broadcast outcome**, and **any subscription that shares PaymentsAPI's app-id or consumer group, or otherwise diverts an event away from it**.

## Accessibility Floor

Behavioral; visual contrast lives in `DESIGN.md`.

- Full keyboard operability for every action Terminal.Gui exposes to the mouse — Tab/arrow/Enter/shortcut keys reach everything (mouse is never a hard requirement, per ADR-015/Terminal.Gui norms).
- Every state is encoded in text **and** a fixed symbol, never color alone (`DESIGN.md` Colors) — this is the floor for color-vision-deficient operators and for any terminal degraded to 16 colors or monochrome.
- **The contrast floor is owed by both palettes, independently.** Neither is a derivation of the other: measured against its own canvas, every token in each palette clears WCAG AA for normal text, and the visual evidence lives in `DESIGN.md` Colors. This is asserted in the test suite rather than trusted, because a palette edit that looks reasonable in a diff is exactly the change that goes unnoticed until it is on a projector. Redundant symbol-plus-label encoding does the real work in both modes; the palettes are why the console is comfortable to read, not how it is understood.
- Focus is always visibly indicated (reverse-video per `DESIGN.md`), and the literal Tab order per workspace is: **topology bar** (resource chip 1…chip N in strip order, then fault chip, then quick-open control 1…M) → **navigation rail** (item 1…5) → **active workspace content** (row 1…N top-to-bottom, then that workspace's primary/contextual action). The old final stop — the evidence strip's Details — is gone with the strip, and the transient announcement does not replace it as a stop (see below). In the **Operations** workspace, "workspace content" is ordered: compose-bar first line (From, To, Submit) → compose-bar second line (Amount, rail chip, idempotency chip, Burst…) → the third compose line where a mode renders one → the focus card's action → STILL OPEN line 1…N; during a burst takeover the content is the takeover, whose only stop is Stop sending, then Done. In the **Faults** workspace, "workspace content" is ordered: preset chip 1…N → error-rate slider → latency-band slider (floor handle, then ceiling handle) → throttling slider → panic-off → Apply, so the destructive-in-spirit control (Apply) is last and the recovery control (panic-off) is reachable before it. `Shift+Tab` reverses the same order exactly. There is no wrap: Tab from the last stop in the active workspace does not cycle back to the topology bar, and `Shift+Tab` from the topology bar's first chip does not cycle to that last stop — an operator who tabs past either end simply stays at that end. The confirmation modal, while open, traps focus entirely inside itself (opens with **Cancel** focused; `Y` confirms, `Escape` cancels; focus returns to the exact control that opened it on either outcome) and is the one place Tab order is fully self-contained rather than shell-wide.
- No content-bearing information is conveyed by text size or weight alone — bold/dim are used for emphasis, never as the only signal of a distinct meaning.
- **Every slider is fully operable and fully readable without the mouse and without color.** Arrow keys step the focused handle, `Shift`+arrow steps coarsely, `Home`/`End` jump to that knob's floor and ceiling. The exact numeric value is always rendered as text beside the track — the bar is reinforcement, never the only way to read the level — so a level survives a monochrome terminal, a screen-reader-less environment, and a projector at the back of the room equally.
- **Panic-off has a single unmodified key (`0`)** reachable from every workspace without first navigating to Faults, because the moment it is needed is the moment navigating is hardest.
- **Feed status is carried in ordinary text**, not in a separate indicator that would need its own focus stop or its own glance — in Evidence it is part of the same string as the elapsed time, in Operations it is the sentence at the right end of the STILL OPEN rule, at the foot of the card region when nothing is open, or on the burst takeover's rule while a burst holds the workspace, and in every case `Outcome unknown` replaces the status label outright. The sentence is present in both directions — listening, or not listening since a stated time — and never degrades to an absence. All of it survives a monochrome terminal, and none of it depends on noticing a change somewhere else on screen.
- **The focus card is a focus stop, not a display.** Its action slot is reached by Tab in the workspace's ordinary order and fires with Enter, so Cancel payment, Look up outcome and Resend same key never require the mouse. Its state is carried by the symbol and the state word together (`⊘ CANCELLED`, `~ AWAITING SETTLEMENT`; cased and weighted per `DESIGN.md` Focus card) rather than by size, weight or colour, and the state word is never abbreviated to fit: the lifecycle line gives up its room first, and the clock after it (see Responsive & Platform).
- **A transient announcement is never the only carrier of what it says.** It takes no focus and never moves the caret — an announcement that stole focus while the operator was typing an account number would be a stage failure — and it is therefore not something an operator can be required to catch. What makes that acceptable is that the same line is an Evidence/Results record from the moment it appears — including a refusal the console produced itself, which nothing else in the system will ever record (see Information Architecture) — and the announcement says so in its own text (`kept in Evidence`), so an operator who was mid-sentence loses proximity and nothing else. The field a refusal names also keeps its own inline marker until the operator changes it, so catching the announcement is never what stands between the operator and knowing the payment was not sent. Its failure meaning rides on its symbol and its words, never on colour alone, exactly like every state above.
- **No confirmation is carried by motion, transience, or color alone.** A settling row may briefly emphasise itself, but the settled state must be fully readable from a static screenshot taken a minute later — symbol, label, timestamps, and balance legs all persist. `[ASSUMPTION]` Any transient emphasis is a brief attribute change (bold/reverse-video) on the row that already changed, not a flash of the whole screen, not a repeating blink, and never longer than about a second; a demo console is watched for an hour at a stretch and a room contains people for whom flashing content is a genuine hazard, not a preference. Terminal.Gui offers no animation primitive worth building this on in any case.
- **Focus and the caret are never moved by an arriving event**, in any state, including behind a confirmation modal (see Interaction Primitives, *A pushed outcome never steals attention*).
- Terminal screen-reader support is not claimed by this spine; accessibility here means keyboard operability and color-independent state, not screen-reader compatibility, which is out of scope for a Terminal.Gui console per the brief's stated non-goals.

## Inspiration & Anti-patterns

- **Lifted (composition only) from [`imports/operator-console-inspiration.png`](imports/operator-console-inspiration.png)**, a user-supplied operator-console composition reference (`.memlog.md` decision) — the transferable principles are: a single near-black work surface, strong verb/object hierarchy, muted command/request detail, simple top-bar controls, and a fixed lower action region — the last of which Operations no longer takes, for reasons argued in Information Architecture. **Rejected explicitly:** its branding, exact colors, labels, and top-tab navigation; this spine uses a compact left rail so workspace switching remains visible without consuming the horizontal status bar. Where the reference and this spine's stated requirements conflict, the spine (this file and `DESIGN.md`) wins. (This is this principle list's one stated home; `DESIGN.md` Brand & Style and this file's Information Architecture cross-reference here rather than restating it.)
- **Rejected — the retired cue player (`mission-critical-talk-v7.json`, `TalkCueDefinition`, `SessionController`'s linear cue track), including its journal/checkpoint/proof-pack recovery machinery.** `SlideAnchor`, `SpeakerNote`, a fixed `Next`-gated sequence, and an append-only journal with a `REHEARSAL`-labeled last-known-good proof pack coupled the tool to one deck version and one recovery model; every deck revision made the tool stale. This spine replaces that with capability-driven workspaces the two talks *use*, never *define*, and with a deliberately simpler recovery contract: rehydrate live Aspire/HTTP state only, start every relaunch with empty operation history, never auto-restore a prior run's local state (see Foundation, Recovery on relaunch). The underlying ports (`IProcessAdapter`, `IHealthMonitor`, `IHttpActionExecutor`, `ILoadWorkflowRunner`, `IBrowserLauncher`, `IJournal`, `IProofPackStore`) and the allow-listed `ActionKind` set survive underneath this new IA — only the presentation/navigation layer and the checkpoint-resume model are retired.
- **Lifted from the Aspire dashboard's resource confidence pattern** — a continuously-refreshed status-chip strip — but reimplemented over the supported `aspire describe --format Json`/`ps` CLI rather than Aspire's private dashboard APIs (ADR-015's explicit boundary).
- **Lifted from the accepted Reset→Run→Wait→Assert→Investigate load-workflow phase strip** (Story 7.1/7.3, spec-add-instant-rail-load-coverage) — reused as-is in the Load Test workspace, not reinvented as a second assertion path.
- **Rejected — a wizard or wizard-like linear onboarding for payment submission.** Presets fill the form immediately; typed override is available but never mandatory, because the operator must be able to fire a payment in seconds mid-sentence.
- **Rejected — a "successful" color/state implied by elapsed time or silence.** Every state above is a first-class typed result; a nine-second instant-rail attempt, and every Resource/AppHost transition, must visibly still be working, not look hung (brief §6).
- **Rejected — color-coded fault severity.** A green/amber/red severity ramp is the obvious first instinct and is wrong here: this console's palette already means proven-pass, proven-fail, and no-proof-yet, and rendering "5% errors" in green would assert a health that nothing measured. Severity is a number, a bar length, and a label; the only thing color says about faults is the binary in-force-or-not (see `DESIGN.md` Do's and Don'ts).
- **Rejected — live-on-drag fault application.** Writing the config on every settled slider position would leak every intermediate value into the running system while the operator is still deciding, and would trigger a Dev Proxy reload per twitch. Staging costs one extra keypress and buys a clean "watch what happens when I do this" beat, which is the entire reason the capability exists on a stage.
- **Rejected — a chaos "scenario runner" that escalates faults on a timer.** It is the retired cue player's linear-sequence mistake in a new costume: it couples the tool to a rehearsed narrative and cannot answer an unplanned "what if it were worse?" from the room. Presets stage a level instantly; the operator decides when, always.
- **Rejected — confirming fault changes with the `Y` modal.** The modal is reserved for actions that destroy state. Faults destroy nothing, are fully reversible, and are undone by one key; gating them behind a modal would make the console's one genuinely dangerous gesture indistinguishable from its safest one, which devalues the modal everywhere it actually matters.
- **Lifted from the system's own existing broadcast (`transaction-events`), not invented for the console.** The four CloudEvents already exist and PaymentsAPI already consumes them; the console adds a listener and nothing else. Nothing is added to CoreBankAPI, PaymentsAPI, or the message contracts to make this console's life easier — a demo tool that required the demonstrated system to be modified for its benefit would be demonstrating the tool.
- **Rejected — a sixth "Events" workspace.** It would make the operator navigate away from a payment to find out whether that payment worked, which inverts the reason the capability exists. The outcome belongs beside the thing it is the outcome of.
- **Rejected — a persistent always-visible event lane in the shell chrome.** It would spend permanent vertical rows in all five workspaces to serve a moment that matters in two, and on an 80×24 terminal that room does not exist.
- **Rejected — a topology-bar chip for feed status.** It is the obvious symmetry with the fault chip, and wrong for the same reason the event lane is: it spends permanent shared chrome on a fact that is only ever interesting while the operator is looking at a specific unresolved payment. Putting it on the row instead makes it strictly stronger — a chip *annotates* a claim that has gone stale, whereas a row that re-states itself as `Outcome unknown` *withdraws* the claim. The console should not be capable of displaying `Awaiting settlement` while it is not listening, and the inline treatment makes that structurally true rather than a rule someone has to remember.
- **Rejected — a full-width "PAYMENT SETTLED" stage banner.** The loudest possible rendering of a claim the console must be able to retract: a contradicting event can arrive after a settlement, and a banner cannot be un-shouted. The same theatrical instinct is better served by the balance legs — `−250.00 → 4,750.00` is more convincing to a sceptical room than any amount of typography, and it stays true.
- **Rejected — inferring an outcome from silence, or from a timeout.** Under injected faults a long wait is the *expected* result, so a timeout that manufactured a `Failed` would fabricate its false negative most reliably in exactly the demo built to provoke it.
- **Rejected — replaying broadcast history when the subscription connects.** It would let a relaunched console present events it never witnessed as though it had, breaking the same "never restore a prior run's state" contract that governs everything else here (see Foundation, Recovery on relaunch).
- **Rejected — resolving a contradiction between HTTP and the broadcast by last-write-wins.** A quiet tie-break would suppress the single most interesting failure this loop can detect. Both facts stay visible and the operator narrates the disagreement.
- **Rejected — reimplementing the Aspire dashboard, Jaeger, or the metrics view inside the console.** These are opened, not rebuilt (brief §9 non-goals); the quick-open cluster in the topology bar is the entire surface for them.

## Key Flows

### Flow 1 — Climax: outage and durable recovery (Loek, mid-talk, either session — the canonical capability sequence)

This exact sequence is the one both named journeys below pass through at their own moment, and the one an operator would replay unscripted if an audience question demanded it — it is described here in capability terms, not slide numbers, precisely because it belongs to no single talk.

1. Loek is in the **Resources** workspace. He selects the `corebank-api` resource row and chooses **Stop**; the confirmation modal names the exact resource and command, opens with **Cancel** focused; he presses `Y` to confirm. The row immediately shows `Running`/`~` plus an elapsed-time readout ("Stopping — 2s") — the visible wait *is* the modal-then-transitioning row, not silent dead air — until Aspire confirms the stop, at which point the row settles to its confirmed real state as Aspire reports it (stopped — an intentional, operator-commanded state, never rendered as `state-failed`/`✕`, which is reserved for a proven failure) and Operations' Submit re-enables.
2. He switches to **Operations** (one keypress) and submits a **standard** payment. The focus card takes it immediately and reads `202 Pending` — truthful, not hung.
3. He submits an **instant** payment against the same stopped dependency. The card takes it the moment he presses Submit, clock running, and the rail has two possible answers here — `504 Cancelled` if it exhausted its budget *and* proved the withdrawal, `202 Pending` if it could prove neither the settlement nor the withdrawal. With CoreBank stopped it is the second that lands: nothing can confirm a cancellation any more than a settlement, so the card holds `202 Pending` (budget exhausted, background delivery continues). That is visibly different narration from the standard rail's routine `202` — same code, different reason, because the instant rail's whole premise is a bounded synchronous budget that just could not be met — and Loek says which of the two answers he is looking at rather than letting the code speak for itself.
4. He switches back to **Resources**, selects the same row — now showing **Restart** in the exact slot **Stop** occupied — confirms with `Y`, and again watches the row's own elapsed-time readout ("Restarting — 3s") until Aspire confirms the restart resolved; only then does every other mutating control re-enable.
5. Throughout the outage, both payments are open at once, which is the case the **STILL OPEN** strip exists for: it appears beneath the card, one compact line each with their clocks climbing past 41s, and the selected one — the instant payment — fills the focus card above them in full. The strip's own rule states `listening since 12:01:04` at its right end, one statement covering both lines beneath it. That statement is the point, and it sits in the region holding the two payments rather than in the shell's chrome: nothing is settling because *the bank is stopped*, not because the console stopped listening, and Loek can say both halves of that sentence while pointing at one part of the screen. Moving the selection to the other line swaps which payment the card prints in full and changes nothing else.
6. Without leaving the console, he switches to **Evidence/Results** and the payments resolve **themselves** — pushed, not polled — as CoreBank comes back: `com.corebank.transaction.completed` rows append to the event feed as the outbox drains, each matching payment row flipping from amber `Awaiting settlement` to green `Settled` in place, and the balance legs landing beneath them — `1001  −250.00 → 4,750.00 EUR`, `2002  +250.00 → 1,180.00 EUR`. The recovery is not a status Loek queries for after the fact; it is a thing the room watches happen. Final evidence — status, both clocks, inbox/outbox state, balance conservation — is on screen, not claimed from memory.

**Failure branch:** if CoreBank does not recover within the talk window, the Resources workspace keeps showing the real (unhealthy) state — never a false Restart-succeeded — and both payments stay visibly `Awaiting settlement` with their clocks climbing rather than being converted into failures by elapsed time. If instead the console's own subscription drops mid-outage, both rows immediately re-state themselves as `Outcome unknown — the console stopped listening at 12:06:02`: the words `Awaiting settlement` leave the screen the moment they stop being true. Loek then reaches for the **Outcome query** — precisely what it is there for — and never claims a settlement the console did not observe.

### Flow 2 — Canonical: turning the system's conditions down while it is running (Loek, mid-talk, either session)

The second capability sequence that belongs to no single talk. Flow 1 proves the system survives a dependency *disappearing*; this one proves it survives a dependency *degrading*, which is both the more common production failure and the harder one to show convincingly — a stopped process is obvious, a slow one is a story you have to make visible.

1. Loek is in **Operations** with a burst of 200 payments running. The burst has taken the whole content area over — no compose bar, no card, no strip — and its **Sent** and **Settled** lines are climbing beneath a rule that still states, at its right end, that the console is listening: the takeover replaces those three surfaces but not the sentence that makes `still moving` mean anything. Every mutating control on screen is dimmed by the single-action-in-flight lock — except the burst's own **Stop sending** and, now, the `accent-teal`-outlined fault controls, which share the same visual signature so the operator can see what is still live without thinking about it.
2. He presses `5`. The **Faults** workspace opens *while the burst keeps running* — this is the moment the whole capability exists for, and it is the reason the fault controls are exempt from the lock.
3. He drags the **latency band** floor to 800 ms and its ceiling to 2000 ms. Nothing changes in the running system yet: each slider shows its live value and its staged value with the delta explicit (`latency 20–200 ms → 800–2000 ms`), and the audience can read the intended change before it happens. That gap between intent and effect is the beat he narrates over.
4. **Climax:** he fires **Apply**. One config write commits both handles at once. The fault chip moves to `Applied — not yet observed in traffic` with an elapsed readout — the console pointedly does *not* claim the faults are live merely because it wrote a file. A second or so later the first intercepted call carries the new band, the chip flips to `Faults in force`, and back in **Operations** the takeover's **Settled** line falls visibly further behind **Sent** while the failed figure stays at zero: slower, not broken. The system degraded and held.
5. He raises the **error rate** to 40% and applies again. Now the **Sent** line's `failed` figure does move, on real injected `503`s — and the **Settled** line's `unknown` figure moves with it, because a `503` on the response path of a call CoreBank may well have executed is not a rejection but a payment whose outcome nobody knows, and the takeover accounts for it rather than letting it fall out of the arithmetic. Every one of them lands in **Evidence/Results** stamped with the fault levels in force when it was captured, so the two halves of the burst can never be confused later.
6. The burst drains, the takeover holds its final summary until he dismisses it, and the compose bar and focus card come back with the latency band still in force. He submits a single **instant** payment into those conditions, and the card takes it on the keypress: `~ AWAITING SETTLEMENT`, clock climbing, **Cancel payment** already live in its action slot because the console holds the payment's id from the moment it sends (see Foundation). This is the moment the room asks what he can actually do about a payment that is hanging, and the answer is one keypress on the object itself — he fires **Cancel payment**, with no modal and no `Y`, because nothing is being destroyed; the action slot reads `Cancelling — 1s` while the state, the clock and the payment stay untouched, since asking is not an outcome. The band is tuned to overrun the rail's budget, so this beat has two truthful endings and Loek narrates whichever he gets. If his cancel lands first, CoreBank answers `200 Cancelled` and the card resolves on that answer to `⊘ CANCELLED`, `withdrawn before execution · no money moved`, `safe to retry with a new key`, with the `com.corebank.transaction.cancelled` broadcast arriving afterwards as confirmation rather than as permission. If the rail's own budget expires first, the *submission* answers `504 Cancelled` and the card resolves to `⊘ CANCELLED BY THE RAIL` without him — the rail withdrew the payment on its own, his cancel became a replay, and CoreBank publishes nothing for a replay, which is exactly why the card never waits for an event to believe an answer it already holds. He says which of the two happened rather than claiming to have caused an outcome the system produced by itself; the point survives either way, because the console showed a proven cancellation and no money moved. Had the bank already executed the payment instead, the same card would now read `● SETTLED` with `too late to cancel — the bank had already executed it` printed above its balance legs. *(This beat previously narrated a card sitting at `202 Pending` while it waited for the bank; that reading predates the rail's cancel-on-budget-exhaustion behaviour and is corrected here.)*
7. He presses `0`. Every knob drops to zero and applies in one step, with no confirmation — because the key that makes things better must never be gated behind the thing currently going wrong. The chip returns to `Armed`, and the payment he resubmits under a fresh key settles inside its budget on screen: same rail, same amount, the only difference being the conditions he just took away. The cancelled card he narrated a minute earlier is untouched by any of it — de-escalating the conditions never rewrites a proven outcome.

**Failure branch:** if the topology was started unarmed, pressing `5` lands on a visibly disabled Faults workspace naming that reason and offering the one-step remedy (restart this AppHost with faults armed) — it never presents live-looking sliders that would silently do nothing. If Dev Proxy never reloads, the chip stays at `Applied — not yet observed in traffic` with the elapsed time climbing, and Loek narrates a proxy that is not picking up its configuration rather than an application that is mysteriously healthy.

### Flow 3 — Canonical: watching two hundred payments prove themselves (Loek, mid-talk, either session)

The third capability sequence that belongs to no single talk. Flow 1 proves the system survives a dependency disappearing and Flow 2 proves it survives one degrading; this one proves something quieter and harder to fake — that the payments the API *accepted* are the same payments the bank actually *finished*. It is the sequence for the moment someone in the room asks the only question that really matters: "yes, but did the money move?"

1. Loek is in **Operations**. He submits a single standard payment. The focus card takes it immediately at `~ AWAITING SETTLEMENT`, `202 Pending`, `0s`, amber, with `listening since 12:01:04` stated at the foot of the card region — nothing else is open, so the card has the whole screen to itself. He says out loud that the API has promised nothing yet, and that the screen is telling him both how long it has been and that something is listening for the answer.
2. A second or so later the card changes **under his finger** — in place, no scroll, no jump — to green `● SETTLED`, with `ProcessedAt 12:04:31.882` and `observed here +222 ms` printed as two separate figures. He points out that the second number is the console's delivery time, not the bank's work.
3. The balance legs land beneath it — `1001  −250.00 → 4,750.00 EUR` and `2002  +250.00 → 1,180.00 EUR`, aligned in their column. This is the beat the whole capability exists for — the room does not have to trust the word "Settled," because the room can see the two account balances move by equal and opposite amounts.
4. He fires a **burst of 200** and it takes the whole workspace over. **Sent** climbs fast and finishes: `Sent 200 / 200 · accepted 200 · failed 0`. **Settled** lags visibly behind it — `Settled 46 · rejected 0 · still moving 154 · unknown 0` — and this gap, held on screen for several seconds, is the demonstration: the API's promise and the bank's completion are two different facts, and everyone can see the distance between them.
5. **Climax:** `still moving` drains to zero. `Settled 200 · rejected 0 · still moving 0 · unknown 0`, against `Sent 200 / 200 · accepted 200 · failed 0` — and only because all three of those figures are zero does the takeover print `every payment proved itself · nothing left awaiting`. Had any send failed or any outcome gone unknown, the same place would have stated the shortfall instead, which is what makes the sentence worth reading aloud. The takeover holds that final summary until he dismisses it, so the room gets to read the result rather than watch it vanish at the moment it becomes true. Nothing was lost between acceptance and completion, and Loek did not have to assert it — he waited, in front of everyone, for a number to reach zero.
6. He switches to **Evidence/Results** and scrolls the event feed: 600 inbound rows, each stamped with its CloudEvent type, transaction id, and both clocks. The feed header states when listening began, so the count on screen is a count of what this console actually witnessed.

**Failure branch:** if the counter *stalls* — `Settled 187 · rejected 0 · still moving 13 · unknown 0` and holding — the console never converts those 13 into failures, and Loek does not get to claim they failed either. The counter answers the obvious question — stuck, or unheard? — by construction: `still moving` is a count of payments the console is currently listening for, the takeover's own rule states that it is listening, and the count cannot survive that statement changing. So those payments are genuinely outstanding and the finding is real. He opens **Evidence/Results** to show the outbox holding them. Had the subscription dropped instead, the **Settled** line would have restated itself on the spot — `Settled 187 · rejected 0 · unknown 13 — the console stopped listening at 12:06:02` — rather than leaving 13 payments pretending to wait, and the honest narration is that the console cannot currently tell — with the **Outcome query** as the way to find out. The console's job in both branches is identical: never let "I stopped hearing about it" and "it did not happen" look the same.

### Flow 4 — Journey A: "Five things every developer should know" (Loek, 250-seat keynote slot, 55 minutes)

1. Before the session, Loek opens **Resources**, starts the Regular AppHost, glances at the topology bar until every resource chip reads `state-healthy`/`●`, then leaves the console on a second display.
2. In **Operations**, he submits one standard payment (the focus card: `202 Pending`), watches the card resolve itself to `● SETTLED` with both balance legs beneath it (Flow 3's opening beats, embedded here), then uses **Resend-same-key** to submit it again with the same idempotency key. The replay produces **no second pair of balance legs** — the clearest possible proof that deduplication held, because the audience is watching for money that does not move.
3. He submits an instant payment from the same preset with the rail switched to `instant`; it settles synchronously (`200 Completed`) within budget, and the broadcast arrives moments later and **agrees** — the card keeps its proven outcome and gains its `ProcessedAt` and its legs. He notes that if the two had disagreed, the console would have shown both and picked neither.
4. **Climax** (Flow 1, embedded here at its narrative moment): stop CoreBank from **Resources**, submit standard + instant from **Operations**, narrate the two rails' answers and why they read the same code for different reasons (Flow 1 step 3), restart, watch recovery in **Evidence/Results**.
5. He opens the metrics view from the topology bar's quick-open cluster to show the queue-duration histogram stretching and collapsing. The topology bar truthfully showed CoreBank stopped during the outage and now confirms the recovered graph is healthy — the point lands on a graph, not a claim.
6. Back in **Operations**, he uses the **burst control** for 200 payments and runs Flow 3's climax on the takeover it opens: **Sent** finishes at `accepted 200`, **Settled** trails it, and he holds the room on `still moving` until it reaches zero — then dismisses the summary and confirms the drain in **Evidence/Results** against the event feed.
7. Bonus: he presses `5` for **Faults**, stages the shipped Regular preset from its preset chips, applies it, waits for the chip to confirm `Faults in force` rather than trusting the write, then returns to **Operations** and submits payments — showing the system absorbing a 5% injected error rate and a 20–200 ms band live. He ends the segment with `0` so the console is provably quiet before the next section starts.

**Failure branch:** if the instant payment cannot settle within budget during step 3 (a real dependency hiccup), the focus card shows whichever of the rail's two budget-exhaustion answers it actually got, and Loek reads that answer rather than a generic one: `504 Cancelled` — `⊘ CANCELLED`, provably withdrawn, nothing moved, safe to retry under a new key — when the withdrawal was proven, or `202 Pending` when it was not and the payment is genuinely still open.
