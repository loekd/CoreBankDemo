### [DemoRunner fault injection workspace](superpowers/specs/2026-09-05-demorunner-fault-injection-workspace-design.md)

- The LoadTests Dev Proxy profile and `k6/script.js` are already mutually incompatible, independent of the Faults workspace: `k6/script.js:148-153` throws unless a fresh `scheme=instant` payment settles inline within the 9000ms `BudgetMilliseconds`, while `CoreBankDemo.LoadTests/devproxy/config/devproxyrc-latency.json` deliberately injects 9500-12000ms on `/api/Transactions/*` — so arming Dev Proxy on the LoadTests topology aborts the k6 run in `setup()` before any assertion executes. — Confirmed by reading `k6/script.js:148-153` against `CoreBankDemo.LoadTests/AppHost.cs:66-72`, whose own comment states the band is tuned to overrun the instant rail's budget; this predates the Faults workspace and is likely why the profile ships `Features:UseDevProxy: false`, and reconciling it is a load-suite decision, not a console change.
- The load-test assertion suite cannot survive injected errors or rate limiting: at minimum `NoFailedMessages`, `NoPendingMessages`, `ExpectedUniqueProcessed`, `AllSubmittedProcessed`, `PerKeyOrdering` and `StageCardinality` fail deterministically once the LoadTests profile injects 503/429/500 or throttles, while `BalanceConservation` and `BalancesCorrect` keep passing vacuously — so a chaos-enabled load run needs a separate fault-tolerant assertion mode. — Confirmed by reading `LoadTestAssertionService.cs:420-523` and `MessageRepositoryBase.ApplyFailureTransition:387-393`; `PerKeyOrdering` is most structural since a terminally-`Failed` row never gets a `ProcessedAt`, and `BalancesCorrect` replays expectations from `Completed` rows alone so it cannot detect a dropped payment — out of scope for the console feature, which only warns before Run when faults are in force.
- `tests/` and `Tests/` resolve to the same directory on this case-insensitive volume, and `dotnet test tests/CoreBankDemo.DemoRunner.Tests/` fails with `MSBUILD : error MSB1050: Specify which project or solution file to use because the folder ... contains more than one project or solution file` — every invocation must pass the `.csproj` path explicitly. — Confirmed during verification of this spec's implementation: `ls -di Tests tests` reports the same inode (29188347), `git config core.ignorecase` is `true`, and `git ls-files` shows 149 files under lowercase `tests/` and none under `Tests/`; pre-existing and unrelated to the Faults workspace.
- DESIGN.md's Do's and Don'ts table contradicts itself on `accent-teal`: row 307 still reads "Use `accent-teal` only for the primary action and focus ring" while row 316 states the three roles the Faults pass established (primary action, focus ring, lock-exempt/faults-in-force); row 316 is the live rule, row 307 is stale. — Confirmed by reading `DESIGN.md:307` against `:316` and the Colors section at `:235-236`, which enumerates the three roles; not corrected during the build since the design spec is a finalized upstream contract, not an implementation artifact.
- Two statements in the finalized `ux-CoreBankDemo-2026-09-03` spines are now factually wrong and need a documentation amendment: `EXPERIENCE.md:28` assumes Dev Proxy's watched-file reload is the mechanism by which levels change on a running proxy, but Dev Proxy 3.2.0 cannot reload its own configuration at all, so the console restarts the `devproxy` Aspire resource after each write instead (ADR-019); and `EXPERIENCE.md:119` justifies the Faults workspace's exemption from the single-action-in-flight lock by claiming a fault change cannot corrupt an in-flight payment, but with a restart in the apply path a call in flight through the proxy can now fail outright rather than merely slow down. The exemption itself still holds since raising a level mid-burst is the demonstration, but its stated justification no longer does. — Measured against a real Dev Proxy 3.2.0 during review loop 2: an atomic temp-then-move write never fires the watcher since it replaces the inode, while an in-place write triggers a self-restart after which the proxy accepts TCP connections and immediately closes them (HTTP 000) and never serves again; not fixed here since the spines are a finalized upstream artifact, so the correction is recorded in this spec's Design Notes and ADR-019 instead.
- `CoreBankDemo.DemoRunner.Tests` intermittently reports a total of one fewer test than usual (369 vs 370, and earlier 347 vs 348) with no failures and `Skipped: 0` in every run — so a test occasionally does not execute, which the build workflow's own Matrix Test Audit treats as equivalent to a missing test. — Observed twice across roughly ten runs by two independent operators and not reproducible on demand; ruled out the suite's only dynamic skip (`CommandRunnerTests.RequirePrintenv`, Windows-only) and its only `TheoryData` source (`AspireAdapterTests.DescribeFailures`, a static literal), so the cause is not identified and worth pinning before this suite is relied on as a CI gate.

### [DemoRunner outcome feedback loop](superpowers/specs/2026-09-05-demorunner-outcome-feedback-loop-design.md)

- A burst can evict every operator-produced evidence record: `MaximumEvidenceRecords` is 500 and each inbound event appends one record, so a 500-payment burst emits up to ~1500 events (a terminal event plus two balance legs each) and flushes the topology, fault, and payment records the export exists to preserve within seconds. Unattributed events from a concurrent load test consume the same budget. — Confirmed by reading `OperatorConsoleOptions.MaximumEvidenceRecords` against `OperatorConsoleController.OnOutcomeEventReceived`, which calls `AddEvidence` once per event including each `balance.updated` leg; not fixed since giving `EvidenceKind.OutcomeEvent` its own bound changes the evidence-record shape the export and Evidence workspace both depend on, a spine decision rather than a defect.
- Each inbound event triggers up to three separate `Update` calls — row resolution, burst counting via `CountForBurst`, and the evidence append — and each raises `StateChanged`, re-projects the whole presentation model, and re-binds the evidence and payment `ListView`s with fresh `ObservableCollection`s. Under a 500-payment burst that is thousands of full re-renders. — Confirmed by reading `OnOutcomeEventReceived`'s call graph against `MainWindow.OnStateChanged` -> `Render` -> `ListBinding.Bind`; the console already has the right tool for this in `TopologyObservationDebouncer`, but batching the three mutations touches the single-mutation-path invariant every other controller command relies on, so it's left as wasteful but correct.
- `TrackedPayments` never reaches the exported evidence. `SessionEvidenceExporter` serializes `IReadOnlyList<EvidenceRecord>` only, so `Contradiction`, `OutcomeUnknown`, and `1 of 2 legs observed` — this feature's headline artifacts — exist only on screen and vanish on quit. — Confirmed by reading `SessionEvidenceExporter` against the new `OperatorConsoleState.TrackedPayments`; not fixed since the export format is a documented artifact consumed outside the console, and adding a second top-level collection is a contract change rather than a patch.
- Nothing preflights `daprd`. The console now needs `daprd` on PATH and three free ports in 53100-53400, but `DoctorRunner` — which already gates on the `devproxy` binary and on per-profile port requirements — has no equivalent check, so the Resources preflight reports a healthy environment for a topology whose feed then fails. — Confirmed by reading `DoctorRunner`'s existing `devproxy` and port requirements against the new `DaprOutcomeFeed.AllocatePortsAsync` and `DaprSidecarProcess`; the spec deliberately reports the missing binary from the spawn failure rather than adding `IsDaprdAvailableAsync` to `IEnvironmentProbe`, and a doctor requirement plus the existing `dapr-install` recipe would be the consistent move but is a scope addition, not a defect.
- `CoreBankDemo.DemoRunner.Tests` reported `Failed: 1` once in a full-solution run and the failing test's name was not captured; it did not recur in ten subsequent runs (six full-solution, four of the process-spawning `DaprSidecarProcessTests` under six saturated cores), all green at 452/452. — Observed once immediately after adding the `daprd` executable resolver during `dotnet test CoreBankDemo.UnitTests.slnf` with no test name captured, and ruled out via targeted stress on the wall-clock-sensitive `DaprSidecarProcessTests` (9/9 passing on four consecutive runs); related in shape to the fault-injection workspace's missing-test entry, worth running with `--logger "console;verbosity=normal"` in CI so the next occurrence names itself.

### [instant rail timeout cancel](superpowers/specs/2026-09-08-instant-rail-timeout-cancel-design.md)

- A destination-account validation rejection (`HttpForwardOutboxDeliveryStrategy.ForwardAsync` throws for `IsValid=false`) is classified as a transport failure, so on the instant rail it now exhausts the attempts, tombstones the id at CoreBank and answers `504 Cancelled` for a deterministic business rejection that could never have executed (previously: `202` and eventual poison `Failed` on the background rail). — Surfaced by the blind-hunter review; the root cause is pre-existing since AD-11 says a business rejection is a completed message with a cached failure payload, but the validate step has no `TransactionSubmission` to complete with and throws instead, so neither the old `202`/`Failed` nor the new `504` is right (`200`/`Failed` is) — not fixed here since it needs a validate-failure outcome on `ICoreBankTransactionForwarder`, a separate change to the delivery-classification contract.
- `TransactionsController.CancelTransaction` records nothing on `BusinessMetrics` (tombstones, pending cancels and `409` refusals are visible only as `Activity` tags), while `ProcessTransaction` records an intake outcome for every path. — Confirmed by reading the new action against `ProcessTransaction`'s `RecordTransactionIntake` calls; the spec named no metric for the cancel operation, and the closed attribute set for `corebankdemo.transaction.intake` would need a new outcome value, a metric-contract change, so it was left out rather than invented.

### [instant rail cancelled event](superpowers/specs/2026-09-08-instant-rail-cancelled-event-design.md)

- DemoRunner burst tally subtracts a submission twice when a terminal broadcast (Settled, Rejected, or now Cancelled) arrives after a feed fault already moved it into `Unknown`; `Math.Max(0, …)` in `BurstProgress.Outstanding` hides the drift. — `OperatorConsoleController.cs` folds `Outstanding` into `Unknown` on feed fault and never reconciles `Unknown` when a late event for one of those ids increments `Settled`/`Rejected`/`CancelledByBroadcast`; the shape predates this story, the cancelled path only mirrors it.
- With `Features:UseDevProxy=true` the LoadTests AppHost sets `NO_PROXY=localhost` while Aspire resolves CoreBank to `http://localhost:<port>`, so PaymentsAPI bypasses Dev Proxy and the latency preset cannot be exercised by the Tier-3 harness. — Six instant probes under the preset all settled inline in ~20 ms during this story's live verification; Dev Proxy configuration was Ask-First for this story, so the residual-202-then-event ordering is proven at Tier 1/2 only.
- Two `balance.updated` legs of one transaction received tens of microseconds apart can be processed in reverse by the two PaymentsAPI replicas, tripping `perKeyOrdering` (stamp-before-commit race), unrelated to cancellation. — Observed once during this story's live verification (`cancel-evt-2`) with parallel out-of-harness submissions; not reproduced by the k6 harness run, which passed.
- `TransactionCancellationHandler` records no `CoreBankOutbox` store-operation `added` metric for the `transaction.cancelled` row it enqueues, unlike `TransactionExecutionHandler` for its rows. — Metrics were out of scope for the cancel endpoint (earlier deferred entry, story instant-rail-timeout-cancel); the event row is a new, uncounted `added` operation on that store.

### [DemoRunner operations stage focus](superpowers/specs/2026-09-09-demorunner-operations-stage-focus-design.md)

- Retiring the standing "Outcome key" field left no way to look up any resolved payment except the most recent one, or any id taken from an Evidence record, another session, or an external log. — Surfaced by the blind-hunter review: `LookUpCardOutcome` can only query `_focusCard.TransactionId`, and `BuildFocusCard` falls back to the last non-open row, so every earlier resolved payment is unreachable from Operations despite EXPERIENCE.md retiring the field as an unchanged capability; needs a UX decision, not a code fix.
- `Q` tears the session down on one unmodified keypress with no confirmation and, since the StatusBar was removed, no on-screen hint that it does; the nav rail advertises `1`-`5` only. — Surfaced by the blind-hunter review and confirmed against `MainWindow.OnKeyDown`; the removed bottom band was the console's only key legend and its removal is a deliberate spine decision, but `Q` is the one key whose stray press ends the demonstration and needs its own UX decision — confirm the quit, re-modify the key, or advertise it elsewhere.

### [evidence payload bodies](superpowers/specs/2026-09-10-evidence-payload-bodies-design.md)

- JournalText.Bound can split a UTF-16 surrogate pair at the 8192-character cut, leaving a lone surrogate in exported JSON. — Pre-existing in JournalRedaction.Apply, but newly reachable from Encoding.UTF8.GetString over arbitrary CloudEvent data rather than only from process output.
- A flood of unrecognised or foreign events on transaction-events can now evict real payment records from the 500-record evidence ring. — HandleAsync no longer drops unparseable messages, so every message on the topic becomes a record; previously only the four known types could.
- Non-UTF-8 CloudEvent data is rendered as replacement characters on a pane that claims to show the bytes as delivered. — Envelope() calls Encoding.UTF8.GetString unconditionally, regardless of the message's DataContentType.
